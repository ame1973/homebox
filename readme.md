# HomeBox

A self-hosted, single-administrator household inventory and asset-management PWA for private LAN/VPN access.

> **Under development. Not ready for production use.** Specification revision v0.9.3 is not an application release. Deployment and usage instructions will be added alongside verified implementations; unimplemented commands are not presented as working features.

## Product scope

- Arbitrarily nested locations, individually tracked units and quantity stock, location/unit QR labels, and shared commercial barcodes.
- A feature-equivalent phone, tablet, and desktop PWA with real live camera scanning, multiple-photo capture, and image search.
- Reviewed OCR/FTS, an optional local AI worker, versioned models, and vector search.
- Purchases, asset lifecycle, per-day/per-use costs, and currency-separated analytics.
- A full offline read replica and explicitly reviewed local drafts: no automatic inventory or financial mutation replay.
- Secure authentication, transactions/idempotency/auditing, verified backup/restore, import/export, and QNAP deployment operations.

## Architecture

Go HTTP server + SQLite WAL/FTS5 + same-origin static React/TypeScript/Vite frontend. The UI uses shadcn/ui/Radix/Tailwind. Private database and media files live on a local filesystem. Production deployments do not require Node.js, and ordinary CRUD must continue with the optional AI worker stopped.

## Database CLI (available now)

The database-maintenance CLI is functional; it is not yet the complete HTTP/PWA application.

```sh
make build
./bin/homebox version
./bin/homebox db migrate --database ./data/homebox.sqlite
./bin/homebox db check --database ./data/homebox.sqlite
```

See [Database Operations](docs/database.md) for private storage permissions, explicit legacy adoption, precision mappings, verified pre-migration snapshots, failure recovery, timeouts, and Linux amd64/arm64 builds. Additive migrations retain independent location, taxonomy, catalog-link, physical Unit/Stock, purchase/allocation and Asset/usage/cost/disposal identities without silently rewriting historical strings, rescaling quantities or claiming full sync readiness. The [owned catalog services and fourteen HTTP operations](docs/catalog-links.md) enforce independent row identity, real barcode validation, complete tag-set replacement and scoped signed collection reads with atomic owner/search updates; typed owned browser adapters and responsive reviewed maintenance screens are available. Local migration snapshots are sensitive, unencrypted database-only recovery files, not full encrypted off-host backups.

## Private setup credential (available now)

With the server stopped and the database already migrated, create a new private setup-token file:

```sh
./bin/homebox auth bootstrap --database ./data/homebox.sqlite --output ./data/bootstrap.token
```

The command prints only the absolute file path and expiry, not the secret. The output directory must be private, the new file is mode `0600`, and existing files/symlinks are never overwritten. The credential expires after 30 minutes and is disabled after successful administrator provisioning. Start the server, open `/setup` on its printed origin, and enter the private code plus the initial account/password. Setup does not sign in automatically: use `/login`, complete the required password change at `/settings/account`, then sign in again with the new password. See [HTTP Authentication and Transport](docs/http-authentication.md) and [Security](docs/security.md) for delivery, failure, and explicit retry behavior. The wider product is still under development.

## Offline account recovery (available now)

A local filesystem owner can replace a forgotten or unsupported legacy password while the server is stopped:

```sh
./bin/homebox auth reset-password --database ./data/homebox.sqlite \
  --output ./data/recovery-password.txt --confirm RESET_PASSWORD
```

The command requires an already provisioned account and explicit confirmation. It generates a random temporary password into a new mode-`0600` private file, prints only account/file/revision metadata, revokes all sessions, and requires password change after the next login. Existing files are never overwritten. Recovery is deliberately unavailable in normal serving-store mode and has no HTTP route. Read the file through a trusted local channel; do not paste secrets into logs or issues. After restarting the server, sign in at `/login` with the temporary password, complete the forced password change, and sign in again. There is deliberately no browser password-reset endpoint.

## Local web application (available now)

The React interface provides real server connectivity, administrator setup/login/password-change/logout, and location management. Open `/locations` after completing the required initial password rotation to browse actual locations, create/edit metadata, move branches, archive/restore, or delete unused leaves. Every location write has an explicit review; conflicts and uncertain results never trigger automatic submission. The same routes and capabilities work on phone, tablet, and desktop, with system/light/dark appearance. See [Location Rules and Usage](docs/locations.md) for the workflow and its remaining contents/photo/history/QR limits. Open `/settings` to manage real category/tag hierarchies and exact names, with reviewed creation, partial edits, leaf-category deletion and tag detachment. See [Categories and Tags](docs/taxonomy.md) for original proofs, conflict adoption, safe retries and item-assignment workflows. Other inventory domains are still being built; no invented inventory data is displayed.

Open `/items` for real catalog metadata, complete server-side filters and signed pages. Create a name/classification/brand/model/measurement record, edit only changed fields, or explicitly archive, restore or delete an unused item. Every write requires review; null versus supplied-empty text and original versions remain explicit. This does not receive stock or create a physical unit/purchase. See [Catalog Item Rules](docs/catalog.md) for safe retries, history guards and the remaining photo-assisted/bulk/import workflows.

From item detail, open the real barcode, alias, attribute or Tag assignment screen. Add/edit/delete independent rows or explicitly replace the complete Tag set, with original Item-versus-row proofs, exact before/after reviews, manual conflict adoption and original-key unknown-result reconciliation. Larger legacy membership remains complete, not truncated to the new-set limit. See [Catalog Links and Tag Membership](docs/catalog-links.md) for routes and usage. These metadata screens do not include camera/scanning or implicitly receive inventory.

The [shared-media groundwork](docs/media.md) preserves unverified historical metadata and independent link identities, exposes authenticated Media metadata and owner- or Media-scoped link-page HTTP reads with stateless browser read adapters, and lets existing Item/Unit/Location deletion atomically advance affected Media memberships without removing sibling links. A protected HTTP operation attaches retained Media to a reviewed owner using the original independent Media and owner proofs. Protected link-edit and unlink operations use only the original independent link proof; unlink returns a frozen acknowledgement with the link tombstone revision while preserving shared Media and other owners. Stateless browser adapters cover all three writes using complete reviewed Media/owner or link snapshots, with explicit original-key reconciliation and no automatic replay. The stateless Media read and attachment adapters and the attachment review screen preserve exact retained slash, backslash, NUL and dot identities using protected query aliases when needed. Browser review-source models complete the selected Media or owner link pages between matching actual source reads, without treating an owner's bracket as proof of current Media metadata. Open **Photo links** from Item, Unit or Location detail to view the complete actual owner-link collection, explicitly review, edit or unlink one independent link, or attach an existing Media record after reviewing both complete scopes. Browse linked or unlinked records in the attachment picker, or enter an exact ID manually. The attachment form warns if the same owner already links that Media; confirmation creates another independent link rather than replacing it. The editor preserves unchanged legacy values and both forms require explicit adoption when reviewed data changes. Retained link IDs containing slash, backslash, NUL or dot segments remain exact through review and the safe query writer; they are not renamed or silently rebased. These screens show metadata only; no image bytes are requested. An internal multipart reader enforces one bounded raw file but is not wired to an upload route. An isolated JPEG/PNG processor validates and re-encodes image bytes and can derive a bounded metadata-free JPEG thumbnail, but neither output is connected to uploads or storage; WebP processing is still pending. The contract also specifies safe file limits, authenticated streams and a bounded global Media metadata index. Protected `GET /api/v1/media`, its stateless browser adapter and the attachment picker read actual linked and unlinked Media with signed live cursors. A discovery page is neither a complete membership proof nor evidence of file integrity; selection re-reads both scopes before review. File storage, global deletion and streams, upload/image gallery/camera, receipt attachments and stored-file integrity verification are not implemented; the partial database backfill does not enable offline sync.

A browser camera-stream lifecycle hook is available for future capture and scanning screens. It requests a live stream only after an explicit action and releases tracks on backgrounding, session purge, completion or unmount, including streams returned by an invalidated pending permission request. Same-origin windows can signal a purge through browser messaging or transient non-secret storage; this camera signal does not clear other windows' private caches. No camera route or capture workflow is available yet; Chromium fake-device tests do not replace physical iPhone/Android acceptance. See [Camera-stream groundwork](docs/media.md#browser-camera-stream-groundwork).

From item detail, open its real Unit list or location quantity balances. All devices share reviewed Unit creation/serial-note editing/movement/status/deletion and exact base-count receipt/consumption/transfer/absolute adjustment. Before/after leg counts, original Item-versus-Unit proofs, full selected paths and explicit conflict/measurement adoption stay visible; uncertain writes keep the original key even after source removal. Catalog filter/cursor returns survive validated login round-trips, but draft amounts and secrets do not. See [Individual Units and Quantity Stock](docs/holdings.md) for routes, archived/zero rules and the linked Asset workflow and remaining public-history/QR/offline limits.

From **Purchases** at `/purchases`, browse real filtered live pages, create an exact merchant/instant/currency header, correct descriptive fields or select a catalog Item and explicitly allocate whole integer minor-unit money and base quantity. Item detail also links its complete associated purchase list. Every financial write requires original-context review and confirmation; changed currency/measurement needs explicit adoption, zero-paid history locks currency, and uncertain replies retain only an explicitly retryable original command. Purchase entry never receives Stock or creates/moves Units. See [Purchases and Financial Allocations](docs/purchases.md) for all routes, exact input examples, safe return/reconciliation behavior and remaining media gates.

All eleven dedicated [Asset financial HTTP operations](docs/assets.md) are implemented: complete nullable profile opt-in/replacement with original Unit/Item/Asset proofs, immutable usage/cost appends with original Asset proofs, dual-proof retirement/disposal, actual detail reads, signed global/owned collections and complete current-posted calculations. They use the normal protected same-origin boundary and SQL revalidation, strict 128 KiB JSON/default-50 paging, independent resource ETags and atomic source/audit/current/outbox/original replies. Exact source-only totals preserve negative net, separate residual projections, null denominators, nanoseconds and inclusive home-civil days. Verified TLS/cookie jars, parser fuzz and actual compiled-server/socket contract checks are separate from schemas/types and hardware acceptance. All eleven stateless runtime Asset browser adapters also preserve whole original review contexts, independent proofs, lossless dates, complete pages and exact summary consistency without hidden reads/retries/storage or replay; strict runtime/type and private actual-SDK/Go browser checks cover them. Complete bracketed Asset sources and all five exact raw form/proposal models are implemented, including explicit nullable/zero decisions, selected correction targets and whole interpretation adoption without conversion. Volatile commands retain each complete original source/body/key; explicit single-flight review preserves uncertain reconciliation through later source changes or a fresh login without replay or historical cache installation. Financial writes refresh dependent Asset/catalog/holding/purchase reads, with location refresh only for potentially physical lifecycle changes. Responsive Asset screens now use these same modules for filtered signed pages, real Unit-based profile opt-in/editing, complete immutable histories, all five reviewed writers and the authoritative current-posted cost table. Open **Assets** at `/assets`, or **Asset** from a Unit detail; new dates/amounts/nullable decisions stay explicit, selected corrections remain immutable and safe scope returns carry no financial drafts. See the [Asset browser usage guide](docs/assets.md#browser-routes-and-usage) for all eleven routes, exact minor-unit/RFC3339 input, separate residual/proceeds, null ratios and uncertain-result recovery. The existing Purchase allocation operation separately updates compatible purchase-basis Asset authority atomically while retaining manual/currency/complete-source/safe-total guards; neither operation implicitly creates or reinterprets a profile.

The root [audited financial correction contracts](docs/financial-corrections.md) additionally define allocation void/replacement, retained disposal state and disposal financial correction/history. Migrations 0017/0018 and private Go services now preserve actual immutable original source, proofs and complete correction history while publishing validated current financial effects. Purchase replacement uses an independently identified new Line; Disposal replacement/void/reinstatement retains the actual independent Disposal subject proof and never changes physical inventory. All five correction HTTP operations, stateless browser adapters, bracketed selected correction sources, pure raw form/proposal models and volatile original-key commands/controller are implemented with strict nested JSON, original independent proofs, scoped live pages and verified HTTP/SDK/form/command tests. The responsive Disposal finance/history screen is available from Asset detail at `/assets/UNIT_ID/disposal-corrections`; it supports explicit financial replacement, void and reinstatement with complete original/current history and original-key review. Purchase detail also links `/purchases/PURCHASE_ID/line-corrections`, which distinguishes current allocations from retained void/replacement decisions and lets an administrator explicitly review a void or complete replacement for an active Line. The same-page replacement selector uses actual filtered signed catalog pages and retains the original Purchase/Line/Item proofs; uncertain results require explicit original-key reconciliation. A financial void is not a physical return or Unit revival; see the [HTTP correction usage guide](docs/financial-corrections.md#protected-http-operations) for reviewed requests and recovery.


Open exactly the `public_origin` printed at startup (by default `http://127.0.0.1:8080`). Development HTTP and insecure cookies are restricted to actual direct loopback peers. Keep this incomplete build on loopback; non-loopback configurations require an explicit HTTPS origin with direct TLS or an explicitly trusted proxy. See [HTTP Authentication and Transport](docs/http-authentication.md) for the implemented flags and API behavior. Production serving uses Go and built static assets, without Node.js. ## Security and data

Use trusted HTTPS over LAN/VPN. See [Security](docs/security.md) for implemented password primitives, cost benchmarking, and the current authentication limits. A VPN does not replace the secure context required by camera/PWA APIs. Do not expose NAS administration, the Docker socket, or unprotected data directories. Do not place SQLite on SMB/NFS. Browser storage can be evicted and is not a durable backup.

Local specifications, environment files, databases, private media, backups, keys, and internal development records are excluded from version control. Public builds and tests must not depend on the local specification pack.

## Development checks

Prerequisites: Linux (including WSL2), Go 1.26.2, Node 24.14.1/npm 11.14.1, Python 3.12, and [uv](https://docs.astral.sh/uv/). The race detector also needs a C compiler; the application SQLite driver itself does not require CGO. Python and Node are development/build tools, not NAS runtime dependencies. Exact dependencies are recorded in `go.sum`, `uv.lock`, and `web/package-lock.json`.

```sh
uv sync --frozen
make setup-web
make check
make test-go-pure
make audit-web
make test-e2e  # Requires the Playwright Chromium browser.

# Run individual tests.
uv run --frozen python -m unittest tests.test_contracts.OpenAPIContractTests.test_entire_document_validates_as_openapi_31 -v
```
