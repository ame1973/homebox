# Shared Images and Media Links

**Availability: authenticated Media metadata/link reads, reviewed owner attachment, link metadata editing and unlinking, with stateless browser adapters, responsive owner-link and existing-Media attachment screens, and database/internal JPEG/PNG/WebP processing, staging and promotion groundwork.** Migration 0019 preserves retained Media/MediaLink source and builds source-only current projections; existing Item, Unit and Location deletion transactions update affected Media membership. Seven protected GET operations expose actual global Media metadata and links for an actual owner or Media. `POST /media/{id}/links` and its exact-identity alias attach retained Media to one reviewed owner; `PATCH` and `DELETE /media/links/{id}` edit or unlink an independently reviewed link through protected Go transactions. `PATCH` and `DELETE /media/links?id=...` are equivalent protected writes for exact retained link identities that cannot be represented in a path. An isolated Go utility validates and re-encodes JPEG, PNG and static WebP bytes; WebP inputs produce sanitized PNG output. The private staged-upload transaction uses it. The private staging and content-addressed promotion helpers are connected to a private SQLite upload transaction. A separate internal per-object recovery primitive handles proven pending stages, but no production HTTP endpoint or startup recovery coordinator uses either path. Production image-file storage, global deletion, streams, an image gallery, upload controls and photo capture are not implemented. Do not treat schemas or database metadata as proof of file safety. Existing catalog, physical holding, purchase and Asset workflows do not depend on an AI worker.

## Identity, ownership and review

A **Media** resource describes one independently versioned image record. When upload is implemented, new uploads must be verified and sanitized; historical records without file-validation evidence are explicitly `unverified`. It is not owned by an Item, Unit or Location. A **MediaLink** is a separate stable identity associating that Media with exactly one actual owner of one of those three kinds. The same Media can have links to several owners. Removing one link must not remove the image, its bytes or another owner's link. Purchase receipt-media workflows are still separate required work; the current three-way owner contract does not pretend that a Purchase is an existing media-link owner.

An `unverified` record preserves its bounded historical MIME, dimensions, byte count and digest as **claims**, not proof that the file exists, matches those values, has a safe format or has had location metadata removed. It may describe a format outside the three supported upload formats. Both thumbnail fields are null, and neither original nor thumbnail content may be streamed on the strength of that record. Migration must not silently mark retained records verified, invent thumbnails or rewrite claims. A later explicit, audited verification/sanitization workflow must inspect the actual file and publish a new Media revision before safe content can be served. A `verified` upload response can contain only JPEG, PNG or WebP, with metadata derived from its actual sanitized bytes. File integrity must still be checked before streaming; a past verification status is not evidence that a file has not since been replaced or corrupted.

A Media revision covers its metadata **and link membership**. Attaching, changing or unlinking a link, including an owner-deletion cascade, must advance the affected Media membership and owner aggregate in the same transaction. This lets a complete Media-before/pages/Media-after review detect an intervening link before global deletion. Existing Item, Unit and Location deletion transactions now validate the complete actual membership of every affected Media, remove only the selected owner's links, emit their independent tombstones and advance each affected Media once. Other owners' links, private bytes and OCR source remain untouched; failure rolls back the owner, counters, current/frozen projections, audit and original reply. The Go attachment, link-edit and unlink transactions are exposed through their protected HTTP operations; global deletion remains unimplemented. A future global Media delete must remove its actual links and emit their independent tombstones, without immediately erasing a deduplicated object still referenced by another Media.

Migration 0023 adds private thumbnail-source rows with a separate digest, dimensions and byte count; it does not create any row for retained Media. A thumbnail row requires a `verified` parent, cannot be reassigned to a different Media, and can share its digest with other Media. Live source reads validate its bounded representation and require that it does not exceed the parent dimensions. Link and owner-deletion transactions include this source in their final unchanged-Media checks. These are database claims, not evidence that a JPEG file exists or matches the digest: the private staged-upload transaction can now create them after real image processing, but no HTTP upload, thumbnail stream or public thumbnail URL is enabled. Public and version-one offline thumbnail fields remain null until an authenticated, integrity-checked stream is available. A future reference-safe object cleanup must check both original storage keys and all thumbnail digests before removing a potentially shared object.

Link writes retain separate original proofs:

| Target operation | Original review proof | Result |
| --- | --- | --- |
| Attach one owner | Media `If-Match` plus required `owner_revision` in the body | New independent `MediaLink` and its own revision-one ETag |
| Change link metadata | That link's original `If-Match` | Actual independent `MediaLink` and its own ETag |
| Unlink | That link's original `If-Match` | Frozen `ActionAck`; its revision is the link tombstone revision |
| Delete Media globally | Original Media membership `If-Match` after reviewing its complete links | Frozen `MediaDeleteResult`; no claim that background file cleanup finished |

All writes require the configured Origin, an active completed session, CSRF, supported client version and an original idempotency key. Authorization and actual source/proofs must be rechecked inside SQL after body reading. A retry uses the identical original key/body/proofs and returns its original committed result; it never silently fetches another proof, rebases or replays on reconnect. The result is reconciliation evidence, not permission to install an old response as current state. A fresh key against changed membership must fail rather than absorb an unseen owner.

For example, the implemented `POST /api/v1/media/{id}/links` accepts this Item body together with the separately reviewed Media `If-Match`:

```json
{
  "item_id": "reviewed-item-id",
  "owner_revision": 12,
  "is_cover": true,
  "sort_order": 0,
  "description": "Front view"
}
```

Exactly one of `item_id`, `item_unit_id` or `location_id` is required and the others must be absent, not null. The owner identity is a JSON value rather than a path segment, so bounded retained IDs containing slash or NUL remain exact and can be selected through the owner-list query. Owner identity cannot be reassigned by a link patch. New sort positions are nonnegative safe integers; retained negative positions remain readable. Setting a new cover while another link for that owner is already a cover returns `MEDIA_COVER_CONFLICT` rather than silently changing it. The link editor can explicitly clear the earlier cover first. Existing multiple legacy covers remain visible and are never silently rewritten; a value-equal patch is still a no-op receipt. Descriptions are bounded plain text, not executable markup or automatically approved OCR.

## Attachment transaction and HTTP boundary

`MediaLibrary.Attach` backs the protected HTTP operation. It accepts the original Media revision and an explicit Item, Unit or Location identity plus its original owner revision. Optional cover/order/description decisions remain distinct in the original request fingerprint, including omission versus an explicit default. The Go service snapshots all caller-owned input pointers before validation and fingerprinting, so later caller changes cannot alter the reviewed owner or link metadata. Creating a cover conflicts with any existing cover for that owner; retained duplicate legacy covers remain visible and are never rewritten implicitly.

The transaction validates actual owner and Media sources/counters and complete memberships in both scopes, including links beyond one page. It creates a new independent revision-one link, advances the Media and affected owner aggregates once, and atomically records current projections, frozen changes, audit and the original response. Item attachment updates the Item aggregate; Unit attachment also advances its owning Item and current location ancestry; Location attachment advances that Location and its ancestors, not descendants. These are metadata revisions, not inventory movements. After publication and session activity, the transaction checks the actual owner source and timestamps, the new link and both memberships, the selected Media and unrelated Media already linked to the owner, and the new current/frozen bytes. A changed or missing reviewed link or related Media causes rollback rather than partial success. Actual source Media and OCR bytes are not modified. Exact original-key reconciliation requires a completed session and survives a fresh login or later owner deletion; a fresh key cannot silently adopt changed proofs.

The service can associate retained unverified Media metadata with an owner; this does not verify that a file exists or authorize streaming its bytes. The path HTTP operation uses the normal completed-session, Origin, CSRF, version and idempotency gates, rejects queries, and strictly reads at most 128 KiB of unencoded JSON with exact names, Unicode and integer values. `POST /api/v1/media-by-identity/links?id=...` uses the same gate, body, original Media and owner proofs, SQL transaction and independent link ETag while preserving one exact bounded Media ID in its query. Identical original commands share a receipt across either URL form, including after a fresh login or owner deletion. The reserved Media ID `links` remains addressable as `POST /api/v1/media/links/links`; the same path with GET lists that Media's membership. Global Media deletion remains future work.

## Link editing transaction and HTTP boundary

`MediaLibrary.PatchLink` updates only supplied `is_cover`, `sort_order` or `description` against the original independent link revision; it cannot reassign its Media or owner and does not require a separate Media or owner proof. It snapshots caller-owned optional values before validation and fingerprinting, preserving omitted versus explicit false/zero/empty intent. A new sort position must be nonnegative, while an omitted legacy negative position remains unchanged. Only a transition from non-cover to cover checks for another existing owner cover. Existing duplicate legacy covers are not silently modified, and an explicitly selected equal value is an audited no-op with no projection revisions.

The transaction validates actual source, counters and complete Media/owner memberships, including links beyond a page. A real change advances the link, Media and actual owner/ancestor scopes atomically, without physical movements, image bytes or unchanged search publication. After audit and session activity, changed and equal decisions recheck actual source, membership and unchanged related Media; an equal decision also checks the original owner projections. Failures roll back the receipt and all source/publication effects. The original key can reconcile its frozen independent link reply after a fresh login or later owner deletion.

`PATCH /api/v1/media/links/{id}` exposes that transaction with the same protected gate and 128-KiB strict JSON boundary as attachment. It requires the original link `If-Match`, accepts one or more of the three metadata fields, and rejects explicit null, unknown or duplicate fields, malformed Unicode, unsafe integers, noncanonical or ambiguous paths and queries. The response and strong ETag identify the independent link, never its Media or owner revision. Dispatch is method-sensitive: `GET /media/links/view` reads Media ID `links`, while `PATCH` or `DELETE /media/links/view` edits or unlinks link ID `view`; `GET` and `POST /media/links/links` read or attach Media ID `links`, while `PATCH` or `DELETE` edits or unlinks link ID `links`. Link IDs that cannot be represented safely in a path remain readable in owner or Media lists; use the exact-query alias described below for their HTTP writes.

`PATCH` and `DELETE /api/v1/media/links?id=...` implement exact retained link identities, including slash, backslash, NUL and dot segments. Each accepts exactly one bounded UTF-8 `id` within a 16-KiB raw query; duplicate, unknown or malformed parameters are rejected without normalizing the identity. These aliases use the same completed-session/Origin/CSRF/version/key gate, independent row proof, strict body rules and authoritative transaction as the existing path writes. An identical original key, identity, body and proof share the same logical receipt across URL forms and can be explicitly reconciled after a fresh login or source deletion; changed intent conflicts. The PATCH reply has the independent link ETag; DELETE returns the tombstone acknowledgement without an ETag. GET on the same path remains the owner-scoped collection. The browser adapters and reviewed edit/unlink screens use these aliases when the retained link ID is not path-addressable.

## Unlink transaction and HTTP boundary

`MediaLibrary.Unlink` accepts the original independent link ID and revision, without an additional Media or owner proof. It validates the actual link, Media, owner and their counters, captures both complete memberships and unrelated owner-linked Media, then removes only the selected row. The link's next revision is a tombstone and the `ActionAck` revision; the actual Media membership and affected owner/ancestor aggregates advance once. This is metadata removal, not physical movement, image-file deletion, OCR editing or unshared-owner cleanup.

After publishing current/frozen changes, audit and session activity, the transaction rechecks the exact owner and Media source/projections, both complete remaining memberships, unchanged related Media, absent link/source projection and the one matching null tombstone. Failures roll back all source, projections and receipts. Explicit same-key reconciliation returns the original acknowledgement after a fresh login or later owner deletion; a different key cannot recreate a removed link. Retained slash/NUL/Unicode identities remain exact in the private service and can now be addressed through the protected query alias.

`DELETE /api/v1/media/links/{id}` exposes unlink through the normal Origin/completed-session/CSRF/version/key gate with the original independent link `If-Match`. It rejects query parameters, a request body and content encoding, then revalidates the session and actual source inside SQL after reading the empty body. The frozen acknowledgement has no ETag; its revision is the link tombstone, not the Media or owner revision. Global Media deletion and file cleanup are separate unfinished work.

## Selected reads and reserved IDs

The private `MediaLibrary.Page` discovers global live Media metadata, including records with no links. It reads actual source and independent counters, validates every returned row and lookahead, and binds its separate 15-minute cursor to principal, dataset epoch and page size. Empty collections have an explicit empty array and null continuation. It exposes no image bytes, private keys or raw OCR; retained unverified claims remain unverified. Protected `GET /api/v1/media` and the stateless `fetchMediaPage` adapter expose this read with completed-session and SQL revalidation. The attachment screen uses these pages to choose an existing record, then reads the selected Media and owner scopes separately for review.

The private `MediaLibrary` store reads actual Media source and independent counters, not current-projection payloads. It pages actual link rows for one existing Item, Unit, Location or Media, validates related Media and owner authority including lookahead, and returns an explicit empty array and null continuation for a real empty collection. Failed source, authorization or cursor checks return no partial page. A joined entry retains the independently versioned Media and link values; neither a private storage key nor raw OCR is returned. The protected HTTP reads use these store methods and neither inspect nor verify image files.

The following authenticated GET operations are implemented under `/api/v1`:

- `GET /media` returns a global metadata page, including unlinked records; it has no collection ETag.
- `GET /media/{id}` returns actual Media metadata and its independent membership ETag.
- `GET /media/{id}/view` returns the identical resource, including a retained ID equal to `links`: the path `/media/links` otherwise names the owner-scoped list. This alias is not another resource or proof.
- `GET /media/links?owner_type=item|unit|location&owner_id=...` returns that real owner's link page.
- `GET /media/{id}/links` returns all owners linked to one real Media, needed before global deletion.
- `GET /media-by-identity?id=...` returns the same actual Media and ETag for an exact retained identity.
- `GET /media-by-identity/links?id=...` pages the same actual Media membership for that identity.

All seven require a completed administrator session and the configured same origin. Collection responses have no ETag; an absent Media or owner is not an empty collection. The separately contracted `POST /media` upload remains unimplemented. `GET /media/{id}/content` and `/media/{id}/thumbnail` are target authenticated image streams and are **not implemented**.

The exact-Media aliases accept slash, backslash, NUL, dot-segment and bounded Unicode identities as query values without renaming them. Metadata and attachment accept exactly one `id`; the membership GET also accepts the existing `limit` and `cursor`. All reject duplicate, unknown, malformed or oversized queries and use the same actual source, independent Media revision and live cursor scope as the corresponding path reads. A continuation can cross the two URL forms only for the same Media, principal, epoch and page size. The stateless browser adapters, bracketed review model and rendered attachment screen select these aliases for path-unaddressable IDs. None of these workflows authorizes file streams or global deletion.

The global page and both link lists use stable ID order, a default of 50, a maximum of 100, required nullable `next_cursor`, and 2048-byte opaque continuations. The HTTP boundary also limits the raw query to 16 KiB. Their independent signatures bind principal, dataset epoch, collection/owner and page size for 15 minutes. Cursor bodies are signed, not encrypted: they contain the continuation resource ID and other paging metadata, but not session credentials or the owner scope. Every page validates real source and lookahead before returning any prefix; link lists also validate their related owners. These are live pages, not frozen sync snapshots or collection ETags. Complete a selected Media's link pages between matching Media reads before deletion. For an owner list, matching owner reads bracket the link collection only: embedded Media metadata can change independently and must be reread under its own proof before a write.

An ETagged `MediaLink` resource includes only the independently versioned link row. List pages instead contain `MediaLinkView` entries: the same flat link fields plus actual separately versioned `media`. This distinction avoids assigning one strong row ETag to response bytes that can change merely because the shared Media changed. Runtime code must check that the embedded Media ID matches `media_id`; JSON Schema cannot compare those fields. A verified thumbnail has both a same-origin derived URL and digest; unavailable or unverified thumbnail metadata has explicit null for both. A schema cannot verify actual bytes, URL identity or that a thumbnail exists. The version-one offline Media payload is unchanged and has no verification field: its retained metadata alone must never be treated as proof of safe bytes. The new source-only backfill sets both thumbnail fields to null; previously frozen or already materialized bytes are preserved exactly, not silently rewritten. Full sync must explicitly validate and reconcile such retained projections before it can expose them, and remains unimplemented.

## Browser adapters

`web/src/lib/api/media.ts` exposes `fetchMediaPage`, `fetchMedia`, `fetchMediaLinksPage` and `fetchOwnerMediaLinksPage`. `fetchMediaPage` reads one global metadata page, including unlinked Media; it rejects duplicate identities and invalid paging representations but does not certify file integrity or complete membership. Each adapter takes a caller-owned `AbortSignal`, sends one same-origin no-store request with an eight-second deadline, and neither paginates automatically nor stores, retries or replays a request. `fetchMedia('links', signal)` selects the reserved-ID escape; owner IDs are query values and can retain valid legacy text that cannot be addressed as a path segment. For Media IDs containing slash, backslash, NUL or a dot segment, the read adapters use the exact-identity query aliases; addressable IDs retain their existing paths. Membership queries validate the combined encoded identity and cursor against the 16-KiB query budget, and cursor limits count decoded UTF-8 bytes.

The adapters check independent Media identity and strong ETag, explicit nullable continuations and absent list ETags, requested owner or Media scope, bounded Unicode and integer fields, distinct link identities, and consistent snapshots for repeated Media within one page. They retain negative legacy link positions and reject an embedded Media whose ID differs from `media_id`. Unverified metadata must have null thumbnail fields; verified metadata must use a supported MIME and either a null pair or a same-origin thumbnail path identifying the same Media plus its digest. A path-unaddressable Media cannot carry a non-null thumbnail path through these adapters. These are representation checks, not proof that a thumbnail or original exists or matches its digest. Separate pages remain live and can change between requests; a future review still needs the actual owner/Media bracketing described above.

`web/src/lib/api/media-writes.ts` exposes `attachMedia`, `patchMediaLink` and `unlinkMediaLink`. Attachment retains the whole original Media and one discriminated Item/Unit/Location snapshot, deriving the JSON owner identity and revision from that same object and the `If-Match` from the Media. It preserves omitted metadata rather than sending default values, and uses the exact-identity query alias if the original Media ID is not path-addressable. Link edit and unlink retain the complete independent link; a validated joined list view is accepted as review context, but its embedded Media is not another proof. The adapters reject a competing loose revision, malformed snapshots, null or unknown metadata and new negative sort positions. For link IDs they retain the existing path when it is addressable and otherwise send exactly one encoded `id` through the query alias; the complete original link and its revision remain mandatory in both cases. Retained owner IDs in attachment JSON, and immutable owner/Media IDs in reviewed links, need not be path-addressable.

For example, after the user reviews the actual Media and Item, a caller can retain the original context and submit:

```ts
const original = {
  media: reviewedMedia,
  owner: { kind: 'item' as const, value: reviewedItem },
  idempotencyKey: crypto.randomUUID(),
}
const body = { is_cover: false }
const link = await attachMedia(reviewedMedia.id, body, { ...original, csrfToken, signal })
```

Callers must obtain the actual source, perform foreground review and retain the original key/body/proofs in volatile memory for an explicit retry; supply a fresh caller-owned CSRF token and cancellation signal when needed. The adapter itself does not provide a review UI. Successful attachment must return the reviewed Media and owner with a new revision-one link and matching ETag. Editing must return the same immutable identities and exact requested/retained fields, with an unchanged revision for equal intent or one advance for an actual change. Unlink must return the next independent tombstone revision without an ETag. Each write has a 30-second deadline, accepts caller-owned CSRF, original idempotency key and cancellation signal, and sends one request only; it never stores credentials, installs a frozen reply as current state, reads a replacement proof, retries, queues or replays on reconnect. A network failure or invalid response can leave a committed result uncertain: retain the original command and key, then reconcile only by explicit foreground action. SQL remains authoritative for current membership and cover conflicts. The browser screens described below use these adapters; image gallery, upload and image streaming remain unavailable.

## Browser upload adapter groundwork

`web/src/lib/api/media-upload.ts` provides a stateless `uploadMedia` adapter for the contracted future upload route. It accepts one caller-owned JPEG, PNG or WebP `Blob` of 1 byte through 32 MiB, sends one multipart `file` part with a fixed non-personal filename, and supplies the normal Origin, CSRF, client version and original idempotency key. It does not include an owner, caller digest, dimensions or `If-Match`; attaching the result is a separate reviewed operation. The browser sets the multipart boundary. TypeScript adapts the generator's binary-as-string request type to `Blob` for this one operation without editing generated declarations or changing the wire contract.

The adapter requires a verified, supported Media response with matching strong ETag, any present thumbnail metadata scoped to that same ID, and bounded image dimensions/output size. A deduplicated response may have a revision greater than one; it is not installed as current state. The adapter sends once, accepts caller cancellation, enforces a 30-second deadline and never queues, refreshes a token or retries on reconnect. If a sent response is lost or canceled, retain the exact original Blob and key for explicit foreground reconciliation; aborting the request does not prove the server did not commit. The adapter does not decode, sanitize, persist or verify image bytes: its MIME and size checks are not server authorization or image validation.

The production `POST /api/v1/media` handler and upload UI are **not implemented**. Node multipart tests and a real Chromium request intercepted with a stubbed success response verify browser serialization and response validation only; they do not establish server publication, recovery or physical-device acceptance.

## Browser review sources

`web/src/features/media/model.ts` completes only the selected live scope. `readMediaMembership` reads the actual Media, every Media-owned link page and the Media again; it returns the collection only when both complete Media snapshots and every joined Media value match. Exact retained Media IDs use the query-aware adapters without changing the identity or bracketing rules. This provides the membership review needed before a future global deletion without inventing owner labels or querying unrelated collections. Media source changes or any link membership change invalidate the bracket. A real empty Media returns an empty link array; a missing or failed Media read is never treated as empty.

`readOwnerMedia` similarly reads the selected Item, Unit or Location before and after all of its owner-link pages. The two full owner snapshots must match, link IDs must be unique, continuations must not cycle, and repeated instances of the same Media must agree across pages. An owner revision covers that owner's link membership, **not** independent Media metadata changes affecting another owner. Even after a successful owner bracket, fetch and review the selected Media separately before using its proof for attachment; do not treat an embedded list view as a fresh Media proof. These live reads are not frozen synchronization snapshots.

For retained owner IDs that cannot be represented as paths, the model reads Items and Units directly through their protected exact-identity queries, including a Unit whose owning Item ID is also path-unaddressable. These reads return the same actual source and aggregate or independent ETag as the respective path detail, without completing the whole catalog. A supplied Item ID is checked against the actual Unit source, not used as another mutation proof. A missing Item or Unit query retains its actual HTTP 404; a failed read is not evidence of absence. The model still finds path-unaddressable Locations and Location ID `tree` in the complete location list; an absent Location established by that list is a local `NOT_FOUND` without an HTTP status. Exact reads do not make ordinary Item or Unit write routes addressable for these IDs. The model never retries or fabricates unqueried owners, Media or collections; the owner-link screen described below consumes it.

## Browser photo links and existing-Media attachment

From an Item, Unit or Location detail page, open **Photo links** to see its complete actual owner-scoped link list, sorted by retained order. The same `/photos` route and capabilities are available at every viewport. It displays cover, description, independent link revision and Media verification metadata; it deliberately does not request or display original or thumbnail bytes. An unverified record is a historical claim, and even a verified status is not a current integrity check. The page distinguishes an absent owner or failed read from a genuinely empty link collection.

Choose **Attach existing photo** to open `/photos/attach`, then open **Browse existing photos** to select from linked or unlinked Media records. The picker requests one live page at a time, with explicit previous, next, first-page and refresh controls. It rejects duplicate identities or cyclic continuations encountered across the visited pages; return to the first page and read again if the listing changes. A failed page is not an empty page. The picker shows metadata claims only, not image bytes, and a listing is neither a complete membership snapshot nor an integrity check. Selection preserves the exact ID and starts fresh owner and Media reads; listing revisions are never used as attachment proofs.

You can also enter an exact ID manually. The default **list format** accepts a quoted JSON string, including escaped control characters; choose **plain text** explicitly to enter an unquoted ID. The formats are never guessed. Plain-text input is subject to browser textarea newline normalization, so use JSON escapes for a retained CR/LF. Slash, backslash, NUL, dot-segment and other valid retained Media identities remain exact; the screen uses the protected identity query when a path cannot represent them. Read the complete selected owner and Media memberships, including the expandable Media-owner link list, before reviewing the original owner and Media revisions. Overlapping rows must agree; a failed or missing read is not an empty collection. If this owner already links the selected Media, the screen warns that confirmation creates another independent link rather than replacing the existing one. Upload is not yet available.

The attachment form starts with an explicit non-cover, zero sort position and empty description. Review and confirm these values or edit them; a new cover cannot silently replace an existing cover. A changed owner or Media requires explicit adoption of both current sources, preserving raw form input, followed by another review. Attachment binds the original Media `If-Match` and original owner revision. It does not copy, upload, read or verify image files. The separately read scopes are live review context, not a frozen server snapshot; SQL remains authoritative at confirmation.

Choose **Edit link** for a selected link to change its cover, sort position or description on `/photos/edit`. The form keeps the reviewed owner scope and independent link revision, displays the exact changed fields before confirmation, and sends only those fields. Untouched negative legacy order and retained text remain unchanged. A new cover cannot silently replace another cover; existing duplicate covers are not automatically repaired. If the current owner or link changes, explicitly adopt its current version while keeping edited raw values, or discard the edits; input that remains invalid must be corrected before review. A missing or failed current read leaves an initialized draft visible but prevents a new write. The draft is volatile and is not restored after leaving the page or losing the session.

Choose **Unlink** on one selected link, review its original independent identity/revision and confirm. Only that association is removed; the Media and other owners remain. A changed owner or link requires another review, not a silent rebase. For attachment, editing or unlinking, if a sent response is uncertain, re-open the original command and explicitly retry the same key; this remains possible after the current owner disappears. Reconnecting never submits a write. The list and editor preserve exact validated owner and link IDs as encoded query values, including retained slash, backslash, NUL and dot identities. The selected link still comes from the complete reviewed owner scope and its own revision remains the only link proof; the adapter selects the exact-query writer when needed. Login retains only the validated owner and, for editing, selected-link identity plus safe list navigation; it does not retain the selected Media for attachment, draft bodies or request keys. `/photos` is intentionally distinct from the server's protected `/media` namespace, which never falls back to the application shell.

## Browser raw form state

`web/src/features/media/form.ts` provides exact volatile values for cover, decimal sort position and description. The new-attachment helper defaults to `false`, `0` and an empty description and sends those values explicitly; the lower-level adapter still preserves omission for callers that choose it. Existing link edits send only changed fields: an unchanged negative legacy position is retained without being submitted or silently repaired. A newly supplied position must be a canonical nonnegative safe integer. Description text is neither trimmed nor Unicode-repaired, and an explicit empty edit clears it.

On explicit adoption of a newer link snapshot, untouched fields use current values and edited fields retain the user's raw text, including malformed or unfinished input for subsequent validation. The independent link, owner and Media identities must remain the same; adoption is never automatic and does not replace the original command retained for an uncertain retry. The rendered attachment and link-edit forms use these helpers; drafts are not persistent.

## Browser review commands

`web/src/features/media/commands.ts` freezes volatile, deeply immutable attachment, link-edit and unlink commands with a new idempotency key. Attachment retains the complete selected owner and Media membership sources; overlapping link rows and their Media values must agree. The sources were read separately, so this consistency check does not make their union a frozen server snapshot or replace SQL validation. Attachment can retain an exact path-unaddressable Media identity and still binds the original Media and owner proofs. Edit and unlink retain the selected complete owner scope and the actual independent link from that scope; the embedded Media is review context, not an extra write proof. These operations can still address a retained link whose Media ID is not path-addressable. New cover conflicts are rejected without silently clearing existing covers; metadata edits and explicit clearing of already duplicated legacy covers remain possible. Omitted negative legacy positions stay unchanged.

`useMediaMutation` composes the shared foreground review controller: review creates no request, confirmation obtains a fresh CSRF token and sends the frozen command once, and sent uncertain failures retain the original key/body/proofs for an explicit retry. It never queues, automatically retries or installs a frozen acknowledgement as current state. Session loss clears volatile review state. Media, catalog, holding, purchase and Asset reads are invalidated after a sent attempt; Unit- and Location-owned links additionally invalidate Location reads. Unit placement can change without changing the link revision, so even a Unit reviewed with no location must invalidate location paths. Existing catalog, owned-row, Location, Holding, taxonomy, Purchase, Asset and financial-correction controllers also invalidate Media reads after a sent write, since owner revisions or link memberships can change. A CSRF failure before dispatch does not invalidate them. The owner-link list, attachment and edit forms, and unlink confirmation consume this controller.

## File and privacy boundary

The intended upload accepts exactly one JPEG, PNG or WebP multipart file, no client storage path, owner, dimensions or digest. The hard wire ceilings are 32 MiB per file, 32 MiB plus 64 KiB for the complete multipart body, 16,384 pixels per dimension and 64 million pixels; an operator may configure stricter limits. Enforce limits for both declared lengths and streaming/chunked bodies, compare declared MIME to magic bytes, and validate a complete supported decode before publication. Unsupported or unsafe animated variants must be rejected rather than treating an unchecked first frame as validation of the whole file.

The internal `httpapi` multipart reader now retains one exact raw file in bounded memory and normalizes its declared MIME without using its filename. It rejects additional fields, encoded parts, ambiguous headers, incomplete input and over-limit declared or actual bodies, including bytes following the final boundary. It does not authenticate, inspect image magic, sanitize bytes, stage files or publish a record; its socket tests use a test-only handler. The production upload route remains unimplemented. A future handler must hold bounded admission through the entire read and processing lifecycle, revalidate authorization, and finish the durable file/SQLite protocol before exposing uploads. A syntactically accepted WebP declaration is not proof that its actual bytes have been decoded or sanitized.

Strip GPS and other sensitive location metadata before storage. Visible text or coordinates photographed into pixels are not removed by metadata stripping. The server derives MIME, dimensions, size and SHA-256 from the actual sanitized bytes; a client filename or digest is never authority, and the stored digest need not equal a raw upload's digest. Bind the original idempotency key to a server-keyed digest of the exact raw file bytes and normalized declared MIME, so files with different private metadata cannot become the same request merely because sanitization yields the same bytes. Do not persist raw file metadata or the caller filename in the receipt. A fresh upload of already verified sanitized content can reuse an existing Media with its actual revision, without implicitly attaching it to an owner. A new identity starts at revision one. Thumbnail JPEG bytes have their own digest; perceptual hashes and visual indexing remain separately validated features, not proof that two photos depict the same object.

The internal store can compute that request fingerprint as a domain-separated HMAC-SHA-256 over the original key, canonical declared MIME and exact raw bytes using its private database-backed server secret. Length framing preserves each value without ambiguous concatenation; hashing checks cancellation in bounded chunks and never returns a partial fingerprint. The caller owns the input bytes and must not change them between fingerprinting and image processing. A JPEG/PNG test demonstrates that two files with different private metadata can sanitize to identical bytes while retaining different original-request fingerprints. A separate test binds the fingerprint to the real generic domain receipt and reconciles it across sessions and a store restart, but does not create a Media record. This helper does not authenticate a caller, validate an image or wire the upload route; the separate image sanitizer performs actual byte validation.

The domain receipt boundary accepts only that typed fingerprint for `post_media`. A committed keyed receipt atomically pins a domain-separated proof of the database server secret; new writes and original-key replays compare the actual database secret and pin again after audit and session activity. A missing or changed pinned secret fails closed instead of silently generating a different key or returning an unreconcilable acknowledgement. The pin is retained even after a receipt expires or the dataset epoch changes; keep the server secret and its matching database state together when making or restoring backups. Migration 0022 does not guess that existing `post_media` receipts were keyed and does not alter them.

The internal Linux `uploadStagedMedia` transaction connects the raw fingerprint to real JPEG/PNG/static-WebP sanitization, separate anonymous original/thumbnail stages, content-addressed promotion and SQLite publication. WebP inputs are re-encoded as PNG while their receipt remains bound to the original declared MIME and raw bytes. It checks an existing original-key receipt before image processing; a fresh request processes both outputs and commits their exact inode journal while they are still unnamed. It then revalidates the completed session, storage bindings and journal inside the authoritative mutation, links and promotes both stages, verifies the actual objects and publishes the source. The SQLite writer transaction remains held across those file operations; large files or slow storage can delay other writers. A new Media, its independent thumbnail source, current/frozen projection, audit, secret pin and original response commit together. A fresh request for the same sanitized content reuses the actual verified Media and its current membership revision only when its original and independently generated thumbnail metadata and bytes match; an unverified or unproven legacy storage-key collision fails closed. It does not attach an owner. The transaction compares complete Media membership, source, current projections and exact pending rows after audit/session activity, and rechecks both files and configured directory bindings before commit. If preserving a journaled stage fails after commit, the returned outcome is uncertain and the original key can reconcile the frozen response.

Before either anonymous inode receives a name, migration 0024's private pending-object journal commits each sealed stage's sanitized digest/size, random intended stage name, inode, staging-directory identity, object-directory identity and dataset epoch. The source mutation rechecks the committed pair, links and promotes through the same anchored directories, and rechecks the configured paths before and after audit/session activity. A successful source transaction retains its exact pending rows and linked stages; only subsequent reference-aware recovery removes them. This keeps a cleanup proof after source COMMIT and after a partial stage unlink. If a process exits or a journal COMMIT returns an error before linking, the anonymous inode closes without leaving a named file; any committed pending rows remain for explicit recovery. Concurrent original-key reconciliation can leave an independent pending pair whose stages are absent. The journal contains no original filename, raw image bytes, request key or session credential.

The internal Linux storage owner derives a private `<database>.media` root from the actual store path. Separate root, `staging` and `objects` owner markers bind the database-instance ID, the device/inode observed when the store opened, a SHA-256 of the resolved database path and each directory's role. An exclusive, nonblocking filesystem lock coordinates cooperating owners. A new owner rejects a different database inode or path, a hard-linked/replaced database, swapped roles, foreign child markers and unmarked nonempty directories without removing their files. Interrupted marker initialization can resume only when its bounded, private partial files match the expected marker prefix. The earlier instance-only `homebox-media-v1` marker is not silently upgraded: its files and marker are retained, and a verified rebind procedure is not yet implemented.

The private upload wrapper serializes preparation and publication and rejects a Media service from another store. It checks database identity before original-key replay and again inside that transaction after session activity; fresh publication also rechecks all role markers and anchored directories after audit/session activity and the final session read. An already-open owner can reconcile a frozen original-key reply even if its Media directories later disappear or change, provided the original database identity remains valid; reopening the owner still requires valid directories. Tests exercise actual separate-process lock contention and release, different and same-path database copies, foreign and swapped child directories, late hard links/marker changes, transaction rollback and close during upload.

These markers and locks are not a complete deletion authority. A copied database can retain the same instance ID; in-place replacement or inode reuse, deliberately copied markers, bind mounts, separately managed copies and same-UID filesystem changes can still defeat assumptions about exclusive ownership. The per-object primitive below also requires matching journal/file identities, epoch and source references, but an automatic coordinator and broader recovery are not implemented. Restoring or relocating a database and media needs a separately verified, explicit rebind procedure. The CLI now rejects known overlaps between the frontend and the derived private Media root at startup, but operators must still exclude mounted aliases, copies and hard links to private Media; see [Data and transport boundaries](security.md#data-and-transport-boundaries).

A pending row alone does **not** prove an object was created by that upload: an unrelated or shared object might already have the same content-derived name. The private Linux recovery primitive lists exact pending identities in explicit live pages of at most 100, validates the lookahead, and processes one selected identity at a time under the storage mutex, cooperative lock and SQLite transaction. It checks the current dataset epoch, database and role-bound directory identities, the exact retained stage name/device/inode, mode, link count, size and actual SHA-256. It separately checks the real object and all current Media original and thumbnail source claims. A verified or unverified original, or any thumbnail that refers to those bytes, keeps the object; only a redundant proven stage can be removed. An existing object with the same digest but a different inode is retained. An object is eligible for deletion only when its actual inode is the same two-link stage inode and no source references it. A missing stage never authorizes deletion of an existing unreferenced object.

Before removing files, recovery validates and snapshots all actual Media sources, private thumbnail claims, Media current projections/counters, other pending rows and the complete sync-state singleton. Noncanonical or corrupt legacy Media claims, orphan thumbnails, changed epochs, substituted files, unexpected hard links and missing referenced objects fail closed for manual review. The implementation currently scans those source and pending scopes twice per selected object; a large backlog can make recovery slow. It rechecks the snapshots after the journal delete and rolls back SQL if a late trigger changes them. File unlink and SQLite COMMIT cannot be one atomic operation: object unlink is synchronized before stage unlink, each attempted unlink is followed by directory/parent synchronization even after cancellation or error, and a retained row can reconcile already-missing files on explicit retry. A returned error can therefore follow a durable file change and is not proof of rollback. Existing original-key receipts and domain data are not rewritten.

An internal bounded batch operation can process one validated page of 1–100 pending identities while holding the same storage lock. Each object is still recovered in its own transaction; it stops at the first error and returns only the number of earlier acknowledged completions. The failed attempt may already have changed files, so the caller must explicitly retry and must not interpret the continuation flag when an error occurs. A later invocation starts from the first remaining row rather than skipping a failed identity. This batching does not run by itself, change source authority or eliminate the full-scope scans.

A separate explicit internal staging audit streams directory entries in bounded pages and checks at most 100,000 non-marker entries against their exact current-epoch journal rows, directory identities, inode, mode, size and link count while holding the storage owner lock. An unknown name, substituted inode, stale row, unsafe mode or excess entry returns an error without a partial count and without removing anything; error text does not include the unknown name. A missing stage does not itself fail this audit. The audit does **not** hash file contents, certify object references, prove that all pending rows have files or run automatically. Recovery must still perform its full source, file and reference checks before cleanup, and unrecognized files require explicit operator review.

An additional explicit internal operation holds the same storage owner lock across that full audit and one recovery page. If the audit finds an unknown or unsafe entry, the operation returns before unlinking any object or stage. If the audit succeeds but a later per-object recovery fails, earlier objects may already be committed and the failed attempt may already have changed files; report only acknowledged completions and explicitly retry from the first remaining row. The audit does not replace the recovery's actual byte/reference checks. This operation is not automatically scheduled and does not expose an HTTP endpoint.

Linux anonymous staging uses `O_TMPFILE` to keep each private, bounded inode unnamed through writing and sealing. It does not fall back to a named file when the filesystem lacks that facility, and closing an anonymous inode never unlinks a conflicting name or unexpected hard link. The journal commits the exact sealed zero-link inode, intended name and directory identities before linking it. If a process exits at that point, explicit recovery can remove the pending rows only after its normal source and object checks; a missing stage never authorizes claiming or deleting an unrelated unreferenced same-digest object. The source mutation verifies that previously committed pair, rechecks the actual anonymous bytes and inode, links each stage without replacement and synchronizes the staging directory even after a link error. It retains and final-checks both journal rows after audit/session writes; a partially linked or promoted stage remains available to explicit recovery. Real subprocess tests cover exit before and after seal, after journal commit, and after linking or promotion before the source transaction commits. This does not clean old unjournaled stages. Linking requires supported Linux filesystem/kernel facilities, using procfs as an alternative when `AT_EMPTY_PATH` is unavailable. QNAP compatibility has not been established, and these tests are not power-loss evidence.

This is **partial internal recovery**, not an automatic service or production upload route. The private page/recovery methods have no HTTP authorization boundary and are not called at server startup; successful uploads retain their journaled stages until this explicit cleanup runs. They do not sweep files without a pending row: older named-stage attempts or external changes can still leave unknown files that require safe manual review. Safe handling of those unknown stages and an automatic coordinator are still required. Tests include real successful and failed uploads, shared references, late SQL changes, actual subprocess exit at several publication points, partial unlink/permission failures and retry; they do not simulate power loss. Same-UID actors and uncoordinated shared mounts remain outside the cooperative lock boundary.

This internal transaction is **not** the production upload route: its caller must bound admission before reading raw bytes and hold it throughout processing, provide trusted private directories, and complete and orchestrate reference-aware crash recovery and cleanup. Failed publication retains potentially shared promoted objects. Authenticated image streaming and the capture/upload UI are still unimplemented. Public and offline thumbnail fields remain null; the returned receipt is reconciliation evidence, not a fresh integrity or membership proof.

A safe implementation must use a private staging area, durable file/directory synchronization, atomic promotion under a server-controlled content key, and recovery for crashes on either side of SQLite COMMIT. Source, counters, current/outbox, audit, idempotent response and any pending-cleanup record commit together. File cleanup runs only after commit and rechecks references, so failed writes, original-key reconciliation, duplicate content or a shared object cannot lose data. Metadata, thumbnails, private originals, receipts and credentials must not enter logs or public caches. A service worker must not cache protected API responses or originals; any future opt-in thumbnail cache has its own privacy and purge policy.

## Browser camera-stream groundwork

The `useCameraStream` hook is a lifecycle building block used by the live preview on `/scan`. Its caller invokes `start` directly from a deliberate user action and passes the current completed-session state. It checks for a secure context and `getUserMedia`, requests video without audio using the rear-facing preference by default, and can explicitly request the front-facing preference. Switching first stops the previous tracks. It never opens or restarts a camera merely because a component mounts, the page becomes visible or a session becomes active.

The hook stops all acquired tracks on completion, unmount, hidden visibility, `pagehide`, a session becoming inactive, or an application's session purge. The purge also blocks a stale mounted caller from reopening a camera until a new inactive-to-active session transition. Same-origin windows signal mounted hooks through `BroadcastChannel` and a transient local-storage fallback containing only the word `cleared`; neither mechanism carries credentials or private data. Cross-window delivery requires at least one of these browser mechanisms to be available. The signal stops camera streams and pending requests; it does not itself purge another window's query cache or future offline replicas. A consumer must pass the current completed-session state, not a stale cached authorization.

A browser permission request cannot itself be canceled: a request invalidated while pending is ignored, and any stream it later returns is immediately stopped. A disconnected/ended video track stops the rest of that stream. Errors are mapped to bounded states without displaying browser diagnostics or device identifiers. The `/scan` preview connects the stream to muted, autoplaying, `playsinline` video with explicit open, close and front/back preference controls. A torch toggle appears only if the active track advertises support; an unsupported or failed torch never changes another stream. A failed video playback can be explicitly retried without reopening the camera. Hardware may ignore an ideal facing preference. A previously completed session can inspect the local camera while offline, but lookups and writes remain disabled until the user explicitly acts online.

This preview uses the browser's available native barcode formats and a local ZXing worker for missing formats as described in [Camera scanning and manual barcode lookup](catalog-links.md#camera-scanning-and-manual-barcode-lookup). It does not take or store photos or provide image-file scanning. Image upload, offline drafts and general cross-window private-cache purge also remain unimplemented. A delivered session-clear signal closes the `/scan` preview and clears that screen's lookup input/results; other mounted routes and future offline replicas are not universally purged, and blocked browser transports can prevent delivery. Automated browser tests use Chromium's fake video device, real worker decoding of independently generated synthetic pixels, a test native detector and a native document permission policy for the denial case; they do not exercise native optical decoding or an operating-system permission prompt. Real iPhone/Android browser and installed-PWA acceptance remains blocked until performed on those devices.

## Video-frame capture groundwork

The internal `captureVideoFrame` helper draws the current live video frame into a fresh canvas and requests a JPEG Blob at quality 0.9. It accepts only a visible, ready video bound to the caller's live video-only stream, and rejects dimensions above 16,384, more than 64 million pixels or an encoded result above 32 MiB without silently resizing it. Browser memory limits may be lower, especially on mobile devices. A failed canvas/encoder, invalid Blob or oversized frame returns a bounded state rather than private device diagnostics.

The caller must verify a completed session and invoke capture from an explicit user action. The helper does not open or stop a camera, store a draft, upload or perform a search. An abort, pagehide, hidden page or delivered session-clear signal discards an in-flight result; after awaiting, the caller must recheck its current session and generation before installing a Blob, and must separately clear any Blob already returned and stop its camera on completion or departure. Canvas encoding cannot be canceled: only one call may remain in flight in a document, and a hung callback locks further captures until a real reload after 30 seconds. Canvas cleanup is best effort, not guaranteed memory erasure.

Browser tests use a private harness to draw real Chromium fake-camera pixels, decode the resulting JPEG, and check late results through session purge, cross-window logout and actual BFCache restoration. The test harness is not a production capture screen and emulation is not physical-device or native permission-prompt acceptance. The Blob is not proof of validated image bytes or stripped metadata; a future upload must still apply the server's full sanitizer and authorization. Production photo capture controls, persistent multi-shot drafts, file fallback, crop/rotation controls, upload and visual search remain unimplemented.

## Captured-photo render groundwork

The internal `renderCapturedPhoto` helper can apply a reviewed crop and quarter-turn to a **current in-memory camera capture** without repeatedly re-encoding intermediate crops. The original captured JPEG wrapper is immutable and recognized only within the current document; arbitrary selected files and restored drafts require a separate validated import path. The helper snapshots the geometry, verifies it against the original capture dimensions, decodes without applying extra orientation metadata and rejects a differently sized bitmap. It draws the selected original pixels once, without resizing or smoothing, and encodes the final result as a JPEG at quality 0.9. The final JPEG is a lossy re-encoding, not an identical byte copy or a guarantee of server-side sanitization.

The caller must enforce a current completed-session gate and explicit action, retain the original capture for future edits, and recheck session/generation after awaiting before installing a result. The caller must discard both source and returned Blobs on session loss, suspension or departure. Abort, hidden visibility, pagehide and delivered session-clear signals discard an in-flight result and clear the canvas best-effort. Browser decoding and encoding cannot be canceled: one render slot remains held across in-app remounts until the pending browser operation finishes; after 30 seconds a hung operation requires a full reload. Best-effort clearing and bitmap close are not memory erasure, and cross-window session signaling remains dependent on at least one available browser transport.

Automated browser tests use a synthetic live-video stream to verify all four rotations against real captured JPEG pixels, and a private fake-camera harness to exercise cross-window logout and actual Chromium BFCache restoration. These are not a production photo editor, image-file importer, uploader, operating-system permission-prompt test or physical-device acceptance.

## Photo crop and rotation geometry

The internal photo geometry model represents a crop as an integer rectangle in the original decoded, oriented pixel source and an independent quarter-turn display orientation. Source dimensions must not exceed 16,384 on either side or 64 million pixels; selections must be nonempty whole-pixel rectangles fully inside the currently displayed image. Rotating preserves the original crop, and a later crop is mapped back into that original coordinate space without changing, resampling or enlarging pixels. Repeated crops and rotations therefore retain exact bounds. The in-memory capture renderer above rejects a decoded source whose actual dimensions differ from the snapshot and uses the captured canvas orientation.

Exhaustive small pixel-grid tests cover every crop in each orientation and repeated edits; a private Chromium test compares the calculated crop with actual canvas pixel transforms. The geometry model itself does not decode or encode a photo, provide an editor, persist a draft, upload or perform visual search. Photo capture and editing controls remain unimplemented.

## Volatile multi-photo editing state

An internal browser model can hold up to ten captures made in the current document, with a 64-MiB aggregate limit on the original encoded JPEG Blobs. It preserves independent local IDs, order, an explicitly chosen optional cover and exact raw descriptions. Retaking a photo replaces its original capture and resets its geometry while preserving its position, cover selection and description; deleting a selected cover clears that selection. Crop and quarter-turn changes use the original-pixel geometry above rather than repeatedly resampling. These limits count source Blob sizes, not decoded pixels or additional rendered preview Blobs; callers must bound those separately.

This model is volatile state only. It neither stores an offline draft nor starts an upload, search or inventory write, and it does not accept selected files or captures restored after a document reload. A future screen must gate camera actions on the current completed session, stop tracks on completion, invalidate late asynchronous results and clear all retained Blobs on session loss, page suspension or departure. Raw descriptions can temporarily contain invalid text; the existing MediaLink writer must validate them before any explicit reviewed attachment. Unit tests use the actual capture helper with a mocked canvas and simulated Blob sizes to exercise transitions and budgets; they are not a photo screen, real memory-pressure test, file fallback, browser permission-prompt test or physical-device acceptance.

## Image processing groundwork

The internal `server/internal/mediaimage` utility accepts JPEG, PNG and static WebP bytes. The private staged-upload transaction uses it, but no HTTP upload calls that transaction. It checks the declared MIME without parameters against the actual format, applies the 32 MiB input, 16,384-per-dimension and 64-million-pixel ceilings before full decoding, and permits callers to specify stricter limits. PNG chunk framing and CRCs are checked across the entire file; APNG control/frame chunks are rejected. JPEG segment and scan framing requires one complete image with no appended data. WebP RIFF sizes, chunk boundaries, padding, still-image membership, metadata flags and EXIF are checked throughout the container; animated variants and mismatched canvas/image dimensions are rejected. Malformed or duplicate EXIF orientation is rejected rather than guessed. Input may already occupy memory: a future HTTP boundary must independently bound and stage the multipart stream before calling it.

After complete decoding, the utility applies the eight TIFF orientation values, then re-encodes JPEG at quality 90 or PNG with the standard Go codecs. A static WebP input is re-encoded losslessly from decoded pixels as PNG, retaining decoded transparency; WebP is not emitted by the decoder-only Go dependency. The output drops source metadata, including GPS and color profiles; stripping color profiles can change displayed colors. The result's MIME, dimensions, byte count and SHA-256 describe the new bytes, not the raw request. Distinct files with different private metadata can produce identical sanitized bytes: future upload idempotency must still bind a server-keyed digest of the exact raw bytes and normalized declared MIME. Visible GPS text in image pixels is not removed. One process-wide decode slot limits simultaneous image processing; large images can still require substantial memory, cancellation is cooperative, and future admission must separately limit concurrent staging.

`SanitizeWithThumbnail` additionally derives a separate JPEG from the same validated, oriented pixels while holding that decode slot. Its longest side is at most 512 pixels, aspect ratio is retained subject to integer rounding, and smaller images are not enlarged. Downscaling averages pixel boxes; transparency is composited onto white. The thumbnail is encoded at JPEG quality 85 without source metadata and has its own actual dimensions, byte count and SHA-256. The original and thumbnail must have distinct output destinations. If either write, processing or cancellation fails, the caller must discard **both** outputs, which may already contain bytes; a returned result is not proof of durable storage or subsequent integrity.

Tests use generated image pixels, independent lossless/lossy/alpha and animated WebP fixtures, actual GPS-bearing EXIF, eight orientations, progressive JPEG scans, 16-bit alpha PNG, thumbnail transparency and downsampling, malformed/truncated data, CRCs, animation rejection, limits, cancellation and fuzzing. The WebP decoder's BSD license is included in [`server/licenses/`](../server/licenses/). This is an internal byte-processing component, not an upload handler, private file store, file-integrity check, recovery protocol or proof of real-device acceptance.

## Private staging groundwork

The Linux store retains an internal named-stage writer as separate filesystem groundwork; the private upload now uses the anonymous staging protocol described above. The named writer requires an existing private local directory, opens its final directory component without following a symlink, creates each random filename exclusively with mode `0600`, and retains a directory descriptor across path renames. Each writer takes an explicit positive output limit, capped at `64,000,000 * 8 + 16 MiB` bytes: re-encoded 16-bit PNG can be larger than the independently bounded 32 MiB raw upload. The caller must supply validated image bytes; the writer does not decode or sanitize them.

A failed, canceled, empty, oversized or changed write cannot be sealed as a successful prefix. Sealing checks the generated name against its actual inode, synchronizes the file, re-reads and hashes the actual bytes against the accepted writes, then synchronizes the staging directory and its parent. Discard remains possible after cancellation and checks the generated inode before unlinking; a failed cleanup can be retried. The inode check and unlink are not atomic against another process with the same Unix UID, which already has unrestricted access to that private directory. A sealed digest is not proof that a file remains unchanged later: promotion rechecks the actual bytes, and future publication and streaming must do so again.

Tests include independent concurrent stages, a real sanitizer producing separate original/thumbnail files, changed bytes and permissions, substituted names/symlinks, a renamed staging directory, cancellation, cleanup failure and a subprocess exiting without cleanup. The subprocess test verifies survival after process exit, not power-loss durability. No HTTP handler or startup path uses this helper yet.

## Content-addressed promotion groundwork

The Linux store can promote a sealed stage to a separate, existing private object directory using a hard link and an internal `sha256-` key derived from the sanitized bytes. Staging and object directories must be distinct and on a filesystem that permits hard links between them; different devices are rejected before changing the stage, and other unsupported cross-mount links fail rather than copying or overwriting. The helper reopens and verifies the staged inode, permissions, byte count and complete SHA-256, changes its mode from `0600` to `0400`, synchronizes the file, and creates the destination name atomically without replacement. It rejects an extra hard link to a writable stage rather than changing another name's permissions.

If the name already exists, promotion never replaces or changes its permissions. It synchronizes the existing file and checks the actual named inode, private directory, regular-file mode (`0400` or `0600`), exact size and full digest before returning a reuse result. Both new and reused objects are subject to directory/parent synchronization and final checks; an error returns no usable result. Cancellation after a link leaves the object in place because another operation may already reference it. Discarding a stage never intentionally deletes the object. A future recovery process must determine references from authoritative SQLite state and coordinate with other producers before removing any abandoned stage or object.

The read-only mode is not immutable storage: a process with the same Unix UID can change permissions or bytes, and inode checks cannot exclude its races. The internal verifier accepts only the digest-derived canonical key and verifies actual bytes at the time of the check; it neither authorizes a read nor protects a later hash-then-stream operation from replacement. The private staged-upload transaction resolves retained storage-key collisions without trusting unverified Media claims, binds idempotency to the exact raw upload and revalidates file/source authority before its SQLite commit. Neither it nor the filesystem helpers implements an HTTP upload endpoint, startup recovery, reference-safe deletion or integrity-checked streams.

Tests cover real sanitizer output, concurrent identical promotions, valid reuse without replacement, tampered bytes, unsafe modes and substituted names, invalid existing objects, exact key validation, actual cross-device rejection where a second filesystem is available, cancellation after linking, and subprocess exit. The subprocess test is not evidence of power-loss recovery.
