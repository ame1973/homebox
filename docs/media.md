# Shared Images and Media Links

**Availability: authenticated Media metadata/link reads, reviewed owner attachment, link metadata editing and unlinking, with stateless browser adapters, responsive owner-link and existing-Media attachment screens, and database/internal JPEG/PNG processing groundwork.** Migration 0019 preserves retained Media/MediaLink source and builds source-only current projections; existing Item, Unit and Location deletion transactions update affected Media membership. Four protected GET operations expose actual Media metadata and links for an actual owner or Media. `POST /media/{id}/links` attaches retained Media to one reviewed owner; `PATCH` and `DELETE /media/links/{id}` edit or unlink an independently reviewed link through protected Go transactions. `PATCH` and `DELETE /media/links?id=...` are equivalent protected writes for exact retained link identities that cannot be represented in a path. An isolated Go utility validates and re-encodes JPEG/PNG bytes, but no upload uses it yet and WebP is not yet supported by that utility. Image-file storage, global deletion, streams, an image gallery, upload controls and camera are not implemented. Do not treat schemas or database metadata as proof of file safety. Existing catalog, physical holding, purchase and Asset workflows do not depend on an AI worker.

## Identity, ownership and review

A **Media** resource describes one independently versioned image record. When upload is implemented, new uploads must be verified and sanitized; historical records without file-validation evidence are explicitly `unverified`. It is not owned by an Item, Unit or Location. A **MediaLink** is a separate stable identity associating that Media with exactly one actual owner of one of those three kinds. The same Media can have links to several owners. Removing one link must not remove the image, its bytes or another owner's link. Purchase receipt-media workflows are still separate required work; the current three-way owner contract does not pretend that a Purchase is an existing media-link owner.

An `unverified` record preserves its bounded historical MIME, dimensions, byte count and digest as **claims**, not proof that the file exists, matches those values, has a safe format or has had location metadata removed. It may describe a format outside the three supported upload formats. Both thumbnail fields are null, and neither original nor thumbnail content may be streamed on the strength of that record. Migration must not silently mark retained records verified, invent thumbnails or rewrite claims. A later explicit, audited verification/sanitization workflow must inspect the actual file and publish a new Media revision before safe content can be served. A `verified` upload response can contain only JPEG, PNG or WebP, with metadata derived from its actual sanitized bytes. File integrity must still be checked before streaming; a past verification status is not evidence that a file has not since been replaced or corrupted.

A Media revision covers its metadata **and link membership**. Attaching, changing or unlinking a link, including an owner-deletion cascade, must advance the affected Media membership and owner aggregate in the same transaction. This lets a complete Media-before/pages/Media-after review detect an intervening link before global deletion. Existing Item, Unit and Location deletion transactions now validate the complete actual membership of every affected Media, remove only the selected owner's links, emit their independent tombstones and advance each affected Media once. Other owners' links, private bytes and OCR source remain untouched; failure rolls back the owner, counters, current/frozen projections, audit and original reply. The Go attachment, link-edit and unlink transactions are exposed through their protected HTTP operations; global deletion remains unimplemented. A future global Media delete must remove its actual links and emit their independent tombstones, without immediately erasing a deduplicated object still referenced by another Media.

Link writes retain separate original proofs:

| Target operation | Original review proof | Result |
| --- | --- | --- |
| Attach one owner | Media `If-Match` plus required `owner_revision` in the body | New independent `MediaLink` and its own revision-one ETag |
| Change link metadata | That link's original `If-Match` | Actual independent `MediaLink` and its own ETag |
| Unlink | That link's original `If-Match` | Frozen `ActionAck`; its revision is the link tombstone revision |
| Delete Media globally | Original Media membership `If-Match` after reviewing its complete links | Frozen `MediaDeleteResult`; no claim that background file cleanup finished |

All writes require the configured Origin, an active completed session, CSRF, supported client version and an original idempotency key. Authorization and actual source/proofs must be rechecked inside SQL after body reading. A retry uses the identical original key/body/proofs and returns its original committed result; it never silently fetches another proof, rebases or replays on reconnect. The result is reconciliation evidence, not permission to install an old response as current state. A fresh key against changed membership must fail rather than absorb an unseen owner.

For example, the implemented `POST /api/v1/media/{id}/links` accepts this Item body together with the separately reviewed Media `If-Match`:

```json
{
  "item_id": "reviewed-item-id",
  "owner_revision": 12,
  "is_cover": true,
  "sort_order": 0,
  "description": "Front view"
}
```

Exactly one of `item_id`, `item_unit_id` or `location_id` is required and the others must be absent, not null. The owner identity is a JSON value rather than a path segment, so bounded retained IDs containing slash or NUL remain exact and can be selected through the owner-list query. Owner identity cannot be reassigned by a link patch. New sort positions are nonnegative safe integers; retained negative positions remain readable. Setting a new cover while another link for that owner is already a cover returns `MEDIA_COVER_CONFLICT` rather than silently changing it. The link editor can explicitly clear the earlier cover first. Existing multiple legacy covers remain visible and are never silently rewritten; a value-equal patch is still a no-op receipt. Descriptions are bounded plain text, not executable markup or automatically approved OCR.

## Attachment transaction and HTTP boundary

`MediaLibrary.Attach` backs the protected HTTP operation. It accepts the original Media revision and an explicit Item, Unit or Location identity plus its original owner revision. Optional cover/order/description decisions remain distinct in the original request fingerprint, including omission versus an explicit default. The Go service snapshots all caller-owned input pointers before validation and fingerprinting, so later caller changes cannot alter the reviewed owner or link metadata. Creating a cover conflicts with any existing cover for that owner; retained duplicate legacy covers remain visible and are never rewritten implicitly.

The transaction validates actual owner and Media sources/counters and complete memberships in both scopes, including links beyond one page. It creates a new independent revision-one link, advances the Media and affected owner aggregates once, and atomically records current projections, frozen changes, audit and the original response. Item attachment updates the Item aggregate; Unit attachment also advances its owning Item and current location ancestry; Location attachment advances that Location and its ancestors, not descendants. These are metadata revisions, not inventory movements. After publication and session activity, the transaction checks the actual owner source and timestamps, the new link and both memberships, the selected Media and unrelated Media already linked to the owner, and the new current/frozen bytes. A changed or missing reviewed link or related Media causes rollback rather than partial success. Actual source Media and OCR bytes are not modified. Exact original-key reconciliation requires a completed session and survives a fresh login or later owner deletion; a fresh key cannot silently adopt changed proofs.

The service can associate retained unverified Media metadata with an owner; this does not verify that a file exists or authorize streaming its bytes. HTTP uses the normal completed-session, Origin, CSRF, version and idempotency gates, rejects queries, and strictly reads at most 128 KiB of unencoded JSON with exact names, Unicode and integer values. A successful response returns the independent link's ETag, not the Media or owner revision. The reserved Media ID `links` is addressable for this operation as `POST /api/v1/media/links/links`; the same path with GET lists that Media's membership. Global Media deletion remains future work.

## Link editing transaction and HTTP boundary

`MediaLibrary.PatchLink` updates only supplied `is_cover`, `sort_order` or `description` against the original independent link revision; it cannot reassign its Media or owner and does not require a separate Media or owner proof. It snapshots caller-owned optional values before validation and fingerprinting, preserving omitted versus explicit false/zero/empty intent. A new sort position must be nonnegative, while an omitted legacy negative position remains unchanged. Only a transition from non-cover to cover checks for another existing owner cover. Existing duplicate legacy covers are not silently modified, and an explicitly selected equal value is an audited no-op with no projection revisions.

The transaction validates actual source, counters and complete Media/owner memberships, including links beyond a page. A real change advances the link, Media and actual owner/ancestor scopes atomically, without physical movements, image bytes or unchanged search publication. After audit and session activity, changed and equal decisions recheck actual source, membership and unchanged related Media; an equal decision also checks the original owner projections. Failures roll back the receipt and all source/publication effects. The original key can reconcile its frozen independent link reply after a fresh login or later owner deletion.

`PATCH /api/v1/media/links/{id}` exposes that transaction with the same protected gate and 128-KiB strict JSON boundary as attachment. It requires the original link `If-Match`, accepts one or more of the three metadata fields, and rejects explicit null, unknown or duplicate fields, malformed Unicode, unsafe integers, noncanonical or ambiguous paths and queries. The response and strong ETag identify the independent link, never its Media or owner revision. Dispatch is method-sensitive: `GET /media/links/view` reads Media ID `links`, while `PATCH` or `DELETE /media/links/view` edits or unlinks link ID `view`; `GET` and `POST /media/links/links` read or attach Media ID `links`, while `PATCH` or `DELETE` edits or unlinks link ID `links`. Link IDs that cannot be represented safely in a path remain readable in owner or Media lists; use the exact-query alias described below for their HTTP writes.

`PATCH` and `DELETE /api/v1/media/links?id=...` implement exact retained link identities, including slash, backslash, NUL and dot segments. Each accepts exactly one bounded UTF-8 `id` within a 16-KiB raw query; duplicate, unknown or malformed parameters are rejected without normalizing the identity. These aliases use the same completed-session/Origin/CSRF/version/key gate, independent row proof, strict body rules and authoritative transaction as the existing path writes. An identical original key, identity, body and proof share the same logical receipt across URL forms and can be explicitly reconciled after a fresh login or source deletion; changed intent conflicts. The PATCH reply has the independent link ETag; DELETE returns the tombstone acknowledgement without an ETag. GET on the same path remains the owner-scoped collection. The browser adapters and reviewed edit/unlink screens use these aliases when the retained link ID is not path-addressable.

## Unlink transaction and HTTP boundary

`MediaLibrary.Unlink` accepts the original independent link ID and revision, without an additional Media or owner proof. It validates the actual link, Media, owner and their counters, captures both complete memberships and unrelated owner-linked Media, then removes only the selected row. The link's next revision is a tombstone and the `ActionAck` revision; the actual Media membership and affected owner/ancestor aggregates advance once. This is metadata removal, not physical movement, image-file deletion, OCR editing or unshared-owner cleanup.

After publishing current/frozen changes, audit and session activity, the transaction rechecks the exact owner and Media source/projections, both complete remaining memberships, unchanged related Media, absent link/source projection and the one matching null tombstone. Failures roll back all source, projections and receipts. Explicit same-key reconciliation returns the original acknowledgement after a fresh login or later owner deletion; a different key cannot recreate a removed link. Retained slash/NUL/Unicode identities remain exact in the private service and can now be addressed through the protected query alias.

`DELETE /api/v1/media/links/{id}` exposes unlink through the normal Origin/completed-session/CSRF/version/key gate with the original independent link `If-Match`. It rejects query parameters, a request body and content encoding, then revalidates the session and actual source inside SQL after reading the empty body. The frozen acknowledgement has no ETag; its revision is the link tombstone, not the Media or owner revision. Global Media deletion and file cleanup are separate unfinished work.

## Selected reads and reserved IDs

The private `MediaLibrary` store reads actual Media source and independent counters, not current-projection payloads. It pages actual link rows for one existing Item, Unit, Location or Media, validates related Media and owner authority including lookahead, and returns an explicit empty array and null continuation for a real empty collection. Failed source, authorization or cursor checks return no partial page. A joined entry retains the independently versioned Media and link values; neither a private storage key nor raw OCR is returned. The protected HTTP reads use these store methods and neither inspect nor verify image files.

The following authenticated GET operations are implemented under `/api/v1`:

- `GET /media/{id}` returns actual Media metadata and its independent membership ETag.
- `GET /media/{id}/view` returns the identical resource, including a retained ID equal to `links`: the path `/media/links` otherwise names the owner-scoped list. This alias is not another resource or proof.
- `GET /media/links?owner_type=item|unit|location&owner_id=...` returns that real owner's link page.
- `GET /media/{id}/links` returns all owners linked to one real Media, needed before global deletion.

All four require a completed administrator session and the configured same origin. Collection responses have no ETag; an absent Media or owner is not an empty collection. `GET /media/{id}/content` and `/media/{id}/thumbnail` are target authenticated image streams and are **not implemented**.

The root contract also defines `GET /media-by-identity?id=...`, `GET /media-by-identity/links?id=...` and `POST /media-by-identity/links?id=...` for retained Media identities that cannot be placed safely in a path. The target reads use the same actual Media revision and live membership cursor as the corresponding path operations; the target attachment uses the same original Media/owner proofs and original-key receipt across both URL forms. These three exact-Media aliases are **contract-only**: HTTP handlers, browser adapters and review screens for path-unaddressable Media IDs are not implemented yet. They do not authorize file streams or global deletion.

The two lists use stable link-ID order, a default of 50, a maximum of 100, required nullable `next_cursor`, and 2048-byte opaque continuations. The HTTP boundary also limits the raw query to 16 KiB. Their independent signatures bind principal, dataset epoch, collection/owner and page size for 15 minutes. Cursor bodies are signed, not encrypted: they contain the continuation link ID and other paging metadata, but not session credentials or the owner scope. Real source, related owners and lookahead are validated before returning any prefix. These are live pages, not frozen sync snapshots or collection ETags. Complete a selected Media's link pages between matching Media reads before deletion. For an owner list, matching owner reads bracket the link collection only: embedded Media metadata can change independently and must be reread under its own proof before a write.

An ETagged `MediaLink` resource includes only the independently versioned link row. List pages instead contain `MediaLinkView` entries: the same flat link fields plus actual separately versioned `media`. This distinction avoids assigning one strong row ETag to response bytes that can change merely because the shared Media changed. Runtime code must check that the embedded Media ID matches `media_id`; JSON Schema cannot compare those fields. A verified thumbnail has both a same-origin derived URL and digest; unavailable or unverified thumbnail metadata has explicit null for both. A schema cannot verify actual bytes, URL identity or that a thumbnail exists. The version-one offline Media payload is unchanged and has no verification field: its retained metadata alone must never be treated as proof of safe bytes. The new source-only backfill sets both thumbnail fields to null; previously frozen or already materialized bytes are preserved exactly, not silently rewritten. Full sync must explicitly validate and reconcile such retained projections before it can expose them, and remains unimplemented.

## Browser adapters

`web/src/lib/api/media.ts` exposes `fetchMedia`, `fetchMediaLinksPage` and `fetchOwnerMediaLinksPage`. Each takes a caller-owned `AbortSignal`, sends one same-origin no-store request with an eight-second deadline, and neither paginates automatically nor stores, retries or replays a request. `fetchMedia('links', signal)` selects the reserved-ID escape; owner IDs are query values and can retain valid legacy text that cannot be addressed as a path segment. Media IDs used in paths must be addressable without slash, backslash, NUL or dot-segment ambiguity.

The adapters check independent Media identity and strong ETag, explicit nullable continuations and absent list ETags, requested owner or Media scope, bounded Unicode and integer fields, distinct link identities, and consistent snapshots for repeated Media within one page. They retain negative legacy link positions and reject an embedded Media whose ID differs from `media_id`. Unverified metadata must have null thumbnail fields; verified metadata must use a supported MIME and either a null pair or a same-origin thumbnail path identifying the same Media plus its digest. These are representation checks, not proof that a thumbnail or original exists or matches its digest. Separate pages remain live and can change between requests; a future review still needs the actual owner/Media bracketing described above.

`web/src/lib/api/media-writes.ts` exposes `attachMedia`, `patchMediaLink` and `unlinkMediaLink`. Attachment retains the whole original Media and one discriminated Item/Unit/Location snapshot, deriving the JSON owner identity and revision from that same object and the `If-Match` from the Media. It preserves omitted metadata rather than sending default values. Link edit and unlink retain the complete independent link; a validated joined list view is accepted as review context, but its embedded Media is not another proof. The adapters reject a competing loose revision, malformed snapshots, unsafe Media path IDs, null or unknown metadata and new negative sort positions. For link IDs they retain the existing path when it is addressable and otherwise send exactly one encoded `id` through the query alias; the complete original link and its revision remain mandatory in both cases. Retained owner IDs in attachment JSON, and immutable owner/Media IDs in reviewed links, need not be path-addressable.

For example, after the user reviews the actual Media and Item, a caller can retain the original context and submit:

```ts
const original = {
  media: reviewedMedia,
  owner: { kind: 'item' as const, value: reviewedItem },
  idempotencyKey: crypto.randomUUID(),
}
const body = { is_cover: false }
const link = await attachMedia(reviewedMedia.id, body, { ...original, csrfToken, signal })
```

Callers must obtain the actual source, perform foreground review and retain the original key/body/proofs in volatile memory for an explicit retry; supply a fresh caller-owned CSRF token and cancellation signal when needed. The adapter itself does not provide a review UI. Successful attachment must return the reviewed Media and owner with a new revision-one link and matching ETag. Editing must return the same immutable identities and exact requested/retained fields, with an unchanged revision for equal intent or one advance for an actual change. Unlink must return the next independent tombstone revision without an ETag. Each write has a 30-second deadline, accepts caller-owned CSRF, original idempotency key and cancellation signal, and sends one request only; it never stores credentials, installs a frozen reply as current state, reads a replacement proof, retries, queues or replays on reconnect. A network failure or invalid response can leave a committed result uncertain: retain the original command and key, then reconcile only by explicit foreground action. SQL remains authoritative for current membership and cover conflicts. The browser screens described below use these adapters; image gallery, upload and image streaming remain unavailable.

## Browser review sources

`web/src/features/media/model.ts` completes only the selected live scope. `readMediaMembership` reads the actual Media, every Media-owned link page and the Media again; it returns the collection only when both complete Media snapshots and every joined Media value match. This provides the membership review needed before a future global deletion without inventing owner labels or querying unrelated collections. Media source changes or any link membership change invalidate the bracket. A real empty Media returns an empty link array; a missing or failed Media read is never treated as empty.

`readOwnerMedia` similarly reads the selected Item, Unit or Location before and after all of its owner-link pages. The two full owner snapshots must match, link IDs must be unique, continuations must not cycle, and repeated instances of the same Media must agree across pages. An owner revision covers that owner's link membership, **not** independent Media metadata changes affecting another owner. Even after a successful owner bracket, fetch and review the selected Media separately before using its proof for attachment; do not treat an embedded list view as a fresh Media proof. These live reads are not frozen synchronization snapshots.

For retained owner IDs that cannot be represented as paths, the model finds Items in the complete unfiltered catalog and Locations in the complete location list, including Location ID `tree`. It reads a path-unaddressable Unit directly through the protected exact-identity query, even if its owning Item ID is also path-unaddressable. A supplied Item ID is checked against the actual Unit source, not used as another mutation proof. An absent selected Item or Location established by a completed fallback list is a local `NOT_FOUND` without an HTTP status; a failed list remains an error, not evidence of absence. A Unit query miss retains its actual HTTP 404. The query makes the Unit readable, but its ordinary Unit mutation routes remain path-only. The model never retries or fabricates unqueried owners, Media or collections; the owner-link screen described below consumes it.

## Browser photo links and existing-Media attachment

From an Item, Unit or Location detail page, open **Photo links** to see its complete actual owner-scoped link list, sorted by retained order. The same `/photos` route and capabilities are available at every viewport. It displays cover, description, independent link revision and Media verification metadata; it deliberately does not request or display original or thumbnail bytes. An unverified record is a historical claim, and even a verified status is not a current integrity check. The page distinguishes an absent owner or failed read from a genuinely empty link collection.

Choose **Attach existing photo** to open `/photos/attach`. There is no global Media index or upload yet: provide the exact ID of an existing record. The default **list format** accepts the quoted JSON string displayed in another link list, including escaped control characters; choose **plain text** explicitly to enter an unquoted ID. The formats are never guessed. Plain-text input is subject to browser textarea newline normalization, so use JSON escapes for a retained CR/LF. The selected Media ID must be addressable by the existing path-based API. Read the complete selected owner and Media memberships, including the expandable Media-owner link list, before reviewing the original owner and Media revisions. Overlapping rows must agree; a failed or missing read is not an empty collection. If this owner already links the selected Media, the screen warns that confirmation creates another independent link rather than replacing the existing one.

The attachment form starts with an explicit non-cover, zero sort position and empty description. Review and confirm these values or edit them; a new cover cannot silently replace an existing cover. A changed owner or Media requires explicit adoption of both current sources, preserving raw form input, followed by another review. Attachment binds the original Media `If-Match` and original owner revision. It does not copy, upload, read or verify image files. The separately read scopes are live review context, not a frozen server snapshot; SQL remains authoritative at confirmation.

Choose **Edit link** for a selected link to change its cover, sort position or description on `/photos/edit`. The form keeps the reviewed owner scope and independent link revision, displays the exact changed fields before confirmation, and sends only those fields. Untouched negative legacy order and retained text remain unchanged. A new cover cannot silently replace another cover; existing duplicate covers are not automatically repaired. If the current owner or link changes, explicitly adopt its current version while keeping edited raw values, or discard the edits; input that remains invalid must be corrected before review. A missing or failed current read leaves an initialized draft visible but prevents a new write. The draft is volatile and is not restored after leaving the page or losing the session.

Choose **Unlink** on one selected link, review its original independent identity/revision and confirm. Only that association is removed; the Media and other owners remain. A changed owner or link requires another review, not a silent rebase. For attachment, editing or unlinking, if a sent response is uncertain, re-open the original command and explicitly retry the same key; this remains possible after the current owner disappears. Reconnecting never submits a write. The list and editor preserve exact validated owner and link IDs as encoded query values, including retained slash, backslash, NUL and dot identities. The selected link still comes from the complete reviewed owner scope and its own revision remains the only link proof; the adapter selects the exact-query writer when needed. Login retains only the validated owner and, for editing, selected-link identity plus safe list navigation; it does not retain the selected Media for attachment, draft bodies or request keys. `/photos` is intentionally distinct from the server's protected `/media` namespace, which never falls back to the application shell.

## Browser raw form state

`web/src/features/media/form.ts` provides exact volatile values for cover, decimal sort position and description. The new-attachment helper defaults to `false`, `0` and an empty description and sends those values explicitly; the lower-level adapter still preserves omission for callers that choose it. Existing link edits send only changed fields: an unchanged negative legacy position is retained without being submitted or silently repaired. A newly supplied position must be a canonical nonnegative safe integer. Description text is neither trimmed nor Unicode-repaired, and an explicit empty edit clears it.

On explicit adoption of a newer link snapshot, untouched fields use current values and edited fields retain the user's raw text, including malformed or unfinished input for subsequent validation. The independent link, owner and Media identities must remain the same; adoption is never automatic and does not replace the original command retained for an uncertain retry. The rendered attachment and link-edit forms use these helpers; drafts are not persistent.

## Browser review commands

`web/src/features/media/commands.ts` freezes volatile, deeply immutable attachment, link-edit and unlink commands with a new idempotency key. Attachment retains the complete selected owner and Media membership sources; overlapping link rows and their Media values must agree. The sources were read separately, so this consistency check does not make their union a frozen server snapshot or replace SQL validation. Edit and unlink retain the selected complete owner scope and the actual independent link from that scope; the embedded Media is review context, not an extra write proof. These operations can still address a retained link whose Media ID is not path-addressable. New cover conflicts are rejected without silently clearing existing covers; metadata edits and explicit clearing of already duplicated legacy covers remain possible. Omitted negative legacy positions stay unchanged.

`useMediaMutation` composes the shared foreground review controller: review creates no request, confirmation obtains a fresh CSRF token and sends the frozen command once, and sent uncertain failures retain the original key/body/proofs for an explicit retry. It never queues, automatically retries or installs a frozen acknowledgement as current state. Session loss clears volatile review state. Media, catalog, holding, purchase and Asset reads are invalidated after a sent attempt; Unit- and Location-owned links additionally invalidate Location reads. Unit placement can change without changing the link revision, so even a Unit reviewed with no location must invalidate location paths. Existing catalog, owned-row, Location, Holding, taxonomy, Purchase, Asset and financial-correction controllers also invalidate Media reads after a sent write, since owner revisions or link memberships can change. A CSRF failure before dispatch does not invalidate them. The owner-link list, attachment and edit forms, and unlink confirmation consume this controller.

## File and privacy boundary

The intended upload accepts exactly one JPEG, PNG or WebP multipart file, no client storage path, owner, dimensions or digest. The hard wire ceilings are 32 MiB per file, 32 MiB plus 64 KiB for the complete multipart body, 16,384 pixels per dimension and 64 million pixels; an operator may configure stricter limits. Enforce limits for both declared lengths and streaming/chunked bodies, compare declared MIME to magic bytes, and validate a complete supported decode before publication. Unsupported or unsafe animated variants must be rejected rather than treating an unchecked first frame as validation of the whole file.

Strip GPS and other sensitive location metadata before storage. Visible text or coordinates photographed into pixels are not removed by metadata stripping. The server derives MIME, dimensions, size and SHA-256 from the actual sanitized bytes; a client filename or digest is never authority, and the stored digest need not equal a raw upload's digest. Bind the original idempotency key to a server-keyed digest of the exact raw file bytes and normalized declared MIME, so files with different private metadata cannot become the same request merely because sanitization yields the same bytes. Do not persist raw file metadata or the caller filename in the receipt. A fresh upload of already verified sanitized content can reuse an existing Media with its actual revision, without implicitly attaching it to an owner. A new identity starts at revision one. Thumbnail JPEG bytes have their own digest; perceptual hashes and visual indexing remain separately validated features, not proof that two photos depict the same object.

A safe implementation must use a private staging area, durable file/directory synchronization, atomic promotion under a server-controlled content key, and recovery for crashes on either side of SQLite COMMIT. Source, counters, current/outbox, audit, idempotent response and any pending-cleanup record commit together. File cleanup runs only after commit and rechecks references, so failed writes, original-key reconciliation, duplicate content or a shared object cannot lose data. Metadata, thumbnails, private originals, receipts and credentials must not enter logs or public caches. A service worker must not cache protected API responses or originals; any future opt-in thumbnail cache has its own privacy and purge policy.

## Image processing groundwork

The internal `server/internal/mediaimage` utility currently accepts JPEG and PNG bytes only. It checks the declared MIME without parameters against the actual format, applies the 32 MiB input, 16,384-per-dimension and 64-million-pixel ceilings before full decoding, and permits callers to specify stricter limits. PNG chunk framing and CRCs are checked across the entire file; APNG control/frame chunks are rejected. JPEG segment and scan framing requires one complete image with no appended data. Malformed or duplicate EXIF orientation is rejected rather than guessed. Input may already occupy memory: a future HTTP boundary must independently bound and stage the multipart stream before calling it.

After complete decoding, the utility applies the eight TIFF orientation values, then re-encodes JPEG at quality 90 or PNG with the standard Go codecs. The output drops source metadata, including GPS and color profiles; stripping color profiles can change displayed colors. The result's MIME, dimensions, byte count and SHA-256 describe the new bytes, not the raw request. Distinct files with different private metadata can produce identical sanitized bytes: future upload idempotency must still bind a server-keyed digest of the exact raw bytes and normalized declared MIME. Visible GPS text in image pixels is not removed. One process-wide decode slot limits simultaneous image processing; large images can still require substantial memory, cancellation is cooperative, and future admission must separately limit concurrent staging.

`SanitizeWithThumbnail` additionally derives a separate JPEG from the same validated, oriented pixels while holding that decode slot. Its longest side is at most 512 pixels, aspect ratio is retained subject to integer rounding, and smaller images are not enlarged. Downscaling averages pixel boxes; transparency is composited onto white. The thumbnail is encoded at JPEG quality 85 without source metadata and has its own actual dimensions, byte count and SHA-256. The original and thumbnail must have distinct output destinations. If either write, processing or cancellation fails, the caller must discard **both** outputs, which may already contain bytes; a returned result is not proof of durable storage or subsequent integrity.

Tests use generated image pixels, actual GPS-bearing EXIF, eight orientations, progressive JPEG scans, 16-bit alpha PNG, thumbnail transparency and downsampling, malformed/truncated data, CRCs, APNG, limits, cancellation and fuzzing. This is an internal byte-processing component, not an upload handler, private file store, file-integrity check, recovery protocol or proof of real-device acceptance. **WebP still needs a supported decoder and complete container/animation validation before the contracted upload can be enabled.**
