# Shared Images and Media Links

**Availability: authenticated Media metadata/link reads and reviewed owner attachment, with database and internal JPEG/PNG processing groundwork.** Migration 0019 preserves retained Media/MediaLink source and builds source-only current projections; existing Item, Unit and Location deletion transactions update affected Media membership. Four protected GET operations expose actual Media metadata and links for an actual owner or Media, with stateless typed browser read adapters. `POST /media/{id}/links` attaches retained Media to one reviewed owner through the protected Go transaction. An isolated Go utility validates and re-encodes JPEG/PNG bytes, but no upload uses it yet and WebP is not yet supported by that utility. Image-file storage, public link editing/unlinking, global deletion, streams, browser attachment UI/SDK, gallery, upload controls and camera are not implemented. Do not treat schemas or database metadata as proof of file safety. Existing catalog, physical holding, purchase and Asset workflows do not depend on an AI worker.

## Identity, ownership and review

A **Media** resource describes one independently versioned image record. When upload is implemented, new uploads must be verified and sanitized; historical records without file-validation evidence are explicitly `unverified`. It is not owned by an Item, Unit or Location. A **MediaLink** is a separate stable identity associating that Media with exactly one actual owner of one of those three kinds. The same Media can have links to several owners. Removing one link must not remove the image, its bytes or another owner's link. Purchase receipt-media workflows are still separate required work; the current three-way owner contract does not pretend that a Purchase is an existing media-link owner.

An `unverified` record preserves its bounded historical MIME, dimensions, byte count and digest as **claims**, not proof that the file exists, matches those values, has a safe format or has had location metadata removed. It may describe a format outside the three supported upload formats. Both thumbnail fields are null, and neither original nor thumbnail content may be streamed on the strength of that record. Migration must not silently mark retained records verified, invent thumbnails or rewrite claims. A later explicit, audited verification/sanitization workflow must inspect the actual file and publish a new Media revision before safe content can be served. A `verified` upload response can contain only JPEG, PNG or WebP, with metadata derived from its actual sanitized bytes. File integrity must still be checked before streaming; a past verification status is not evidence that a file has not since been replaced or corrupted.

A Media revision covers its metadata **and link membership**. Attaching, changing or unlinking a link, including an owner-deletion cascade, must advance the affected Media membership and owner aggregate in the same transaction. This lets a complete Media-before/pages/Media-after review detect an intervening link before global deletion. Existing Item, Unit and Location deletion transactions now validate the complete actual membership of every affected Media, remove only the selected owner's links, emit their independent tombstones and advance each affected Media once. Other owners' links, private bytes and OCR source remain untouched; failure rolls back the owner, counters, current/frozen projections, audit and original reply. The Go attachment transaction and protected HTTP endpoint implement the first operation below; private Go link editing is implemented, while its HTTP handler, unlink and global deletion remain unimplemented. A future global Media delete must remove its actual links and emit their independent tombstones, without immediately erasing a deduplicated object still referenced by another Media.

Link writes retain separate original proofs:

| Target operation | Original review proof | Result |
| --- | --- | --- |
| Attach one owner | Media `If-Match` plus required `owner_revision` in the body | New independent `MediaLink` and its own revision-one ETag |
| Change link metadata | That link's original `If-Match` | Actual independent `MediaLink` and its own ETag |
| Unlink | That link's original `If-Match` | Frozen `ActionAck`; its revision is the link tombstone revision |
| Delete Media globally | Original Media membership `If-Match` after reviewing its complete links | Frozen `MediaDeleteResult`; no claim that background file cleanup finished |

All writes require the configured Origin, an active completed session, CSRF, supported client version and an original idempotency key. Authorization and actual source/proofs must be rechecked inside SQL after body reading. A retry uses the identical original key/body/proofs and returns its original committed result; it never silently fetches another proof, rebases or replays on reconnect. The result is reconciliation evidence, not permission to install an old response as current state. A fresh key against changed membership must fail rather than absorb an unseen owner.

For example, the implemented `POST /api/v1/media/{id}/links` accepts this Item body together with the separately reviewed Media `If-Match`:

```json
{
  "item_id": "reviewed-item-id",
  "owner_revision": 12,
  "is_cover": true,
  "sort_order": 0,
  "description": "Front view"
}
```

Exactly one of `item_id`, `item_unit_id` or `location_id` is required and the others must be absent, not null. The owner identity is a JSON value rather than a path segment, so bounded retained IDs containing slash or NUL remain exact and can be selected through the owner-list query. Owner identity cannot be reassigned by a link patch. New sort positions are nonnegative safe integers; retained negative positions remain readable. Setting a new cover while another link for that owner is already a cover returns `MEDIA_COVER_CONFLICT` rather than silently changing it. A future user-facing link-edit workflow can explicitly clear the earlier cover first. Existing multiple legacy covers remain visible and are never silently rewritten; a value-equal patch is still a no-op receipt. Descriptions are bounded plain text, not executable markup or automatically approved OCR.

## Attachment transaction and HTTP boundary

`MediaLibrary.Attach` backs the protected HTTP operation. It accepts the original Media revision and an explicit Item, Unit or Location identity plus its original owner revision. Optional cover/order/description decisions remain distinct in the original request fingerprint, including omission versus an explicit default. The Go service snapshots all caller-owned input pointers before validation and fingerprinting, so later caller changes cannot alter the reviewed owner or link metadata. Creating a cover conflicts with any existing cover for that owner; retained duplicate legacy covers remain visible and are never rewritten implicitly.

The transaction validates actual owner and Media sources/counters and complete memberships in both scopes, including links beyond one page. It creates a new independent revision-one link, advances the Media and affected owner aggregates once, and atomically records current projections, frozen changes, audit and the original response. Item attachment updates the Item aggregate; Unit attachment also advances its owning Item and current location ancestry; Location attachment advances that Location and its ancestors, not descendants. These are metadata revisions, not inventory movements. After publication and session activity, the transaction checks the actual owner source and timestamps, the new link and both memberships, the selected Media and unrelated Media already linked to the owner, and the new current/frozen bytes. A changed or missing reviewed link or related Media causes rollback rather than partial success. Actual source Media and OCR bytes are not modified. Exact original-key reconciliation requires a completed session and survives a fresh login or later owner deletion; a fresh key cannot silently adopt changed proofs.

The service can associate retained unverified Media metadata with an owner; this does not verify that a file exists or authorize streaming its bytes. HTTP uses the normal completed-session, Origin, CSRF, version and idempotency gates, rejects queries, and strictly reads at most 128 KiB of unencoded JSON with exact names, Unicode and integer values. A successful response returns the independent link's ETag, not the Media or owner revision. The reserved Media ID `links` is addressable for this operation as `POST /api/v1/media/links/links`; the same path with GET lists that Media's membership. Private Go link editing is available, but its HTTP handler, unlinking, global deletion and browser attachment UI/SDK remain future work.

## Private link editing

`MediaLibrary.PatchLink` updates only supplied `is_cover`, `sort_order` or `description` against the original independent link revision; it cannot reassign its Media or owner and does not require a separate Media or owner proof. It snapshots caller-owned optional values before validation and fingerprinting, preserving omitted versus explicit false/zero/empty intent. A new sort position must be nonnegative, while an omitted legacy negative position remains unchanged. Only a transition from non-cover to cover checks for another existing owner cover. Existing duplicate legacy covers are not silently modified, and an explicitly selected equal value is an audited no-op with no projection revisions.

The transaction validates actual source, counters and complete Media/owner memberships, including links beyond a page. A real change advances the link, Media and actual owner/ancestor scopes atomically, without physical movements, image bytes or unchanged search publication. After audit and session activity, changed and equal decisions recheck actual source, membership and unchanged related Media; an equal decision also checks the original owner projections. Failures roll back the receipt and all source/publication effects. The original key can reconcile its frozen independent link reply after a fresh login or later owner deletion. This is a private Go transaction only; no HTTP link PATCH, browser adapter or review screen is available yet.

## Selected reads and reserved IDs

The private `MediaLibrary` store reads actual Media source and independent counters, not current-projection payloads. It pages actual link rows for one existing Item, Unit, Location or Media, validates related Media and owner authority including lookahead, and returns an explicit empty array and null continuation for a real empty collection. Failed source, authorization or cursor checks return no partial page. A joined entry retains the independently versioned Media and link values; neither a private storage key nor raw OCR is returned. The protected HTTP reads use these store methods and neither inspect nor verify image files.

The following authenticated GET operations are implemented under `/api/v1`:

- `GET /media/{id}` returns actual Media metadata and its independent membership ETag.
- `GET /media/{id}/view` returns the identical resource, including a retained ID equal to `links`: the path `/media/links` otherwise names the owner-scoped list. This alias is not another resource or proof.
- `GET /media/links?owner_type=item|unit|location&owner_id=...` returns that real owner's link page.
- `GET /media/{id}/links` returns all owners linked to one real Media, needed before global deletion.

All four require a completed administrator session and the configured same origin. Collection responses have no ETag; an absent Media or owner is not an empty collection. `GET /media/{id}/content` and `/media/{id}/thumbnail` are target authenticated image streams and are **not implemented**.

The two lists use stable link-ID order, a default of 50, a maximum of 100, required nullable `next_cursor`, and 2048-byte opaque continuations. The HTTP boundary also limits the raw query to 16 KiB. Their independent signatures bind principal, dataset epoch, collection/owner and page size for 15 minutes. Cursor bodies are signed, not encrypted: they contain the continuation link ID and other paging metadata, but not session credentials or the owner scope. Real source, related owners and lookahead are validated before returning any prefix. These are live pages, not frozen sync snapshots or collection ETags. Complete a selected Media's link pages between matching Media reads before deletion. For an owner list, matching owner reads bracket the link collection only: embedded Media metadata can change independently and must be reread under its own proof before a write.

An ETagged `MediaLink` resource includes only the independently versioned link row. List pages instead contain `MediaLinkView` entries: the same flat link fields plus actual separately versioned `media`. This distinction avoids assigning one strong row ETag to response bytes that can change merely because the shared Media changed. Runtime code must check that the embedded Media ID matches `media_id`; JSON Schema cannot compare those fields. A verified thumbnail has both a same-origin derived URL and digest; unavailable or unverified thumbnail metadata has explicit null for both. A schema cannot verify actual bytes, URL identity or that a thumbnail exists. The version-one offline Media payload is unchanged and has no verification field: its retained metadata alone must never be treated as proof of safe bytes. The new source-only backfill sets both thumbnail fields to null; previously frozen or already materialized bytes are preserved exactly, not silently rewritten. Full sync must explicitly validate and reconcile such retained projections before it can expose them, and remains unimplemented.

## Browser read adapters

`web/src/lib/api/media.ts` exposes `fetchMedia`, `fetchMediaLinksPage` and `fetchOwnerMediaLinksPage`. Each takes a caller-owned `AbortSignal`, sends one same-origin no-store request with an eight-second deadline, and neither paginates automatically nor stores, retries or replays a request. `fetchMedia('links', signal)` selects the reserved-ID escape; owner IDs are query values and can retain valid legacy text that cannot be addressed as a path segment. Media IDs used in paths must be addressable without slash, backslash, NUL or dot-segment ambiguity.

The adapters check independent Media identity and strong ETag, explicit nullable continuations and absent list ETags, requested owner or Media scope, bounded Unicode and integer fields, distinct link identities, and consistent snapshots for repeated Media within one page. They retain negative legacy link positions and reject an embedded Media whose ID differs from `media_id`. Unverified metadata must have null thumbnail fields; verified metadata must use a supported MIME and either a null pair or a same-origin thumbnail path identifying the same Media plus its digest. These are representation checks, not proof that a thumbnail or original exists or matches its digest. Separate pages remain live and can change between requests; a future review still needs the actual owner/Media bracketing described above. Browser gallery, upload, mutation adapters/screens and image streaming remain unavailable.

## File and privacy boundary

The intended upload accepts exactly one JPEG, PNG or WebP multipart file, no client storage path, owner, dimensions or digest. The hard wire ceilings are 32 MiB per file, 32 MiB plus 64 KiB for the complete multipart body, 16,384 pixels per dimension and 64 million pixels; an operator may configure stricter limits. Enforce limits for both declared lengths and streaming/chunked bodies, compare declared MIME to magic bytes, and validate a complete supported decode before publication. Unsupported or unsafe animated variants must be rejected rather than treating an unchecked first frame as validation of the whole file.

Strip GPS and other sensitive location metadata before storage. Visible text or coordinates photographed into pixels are not removed by metadata stripping. The server derives MIME, dimensions, size and SHA-256 from the actual sanitized bytes; a client filename or digest is never authority, and the stored digest need not equal a raw upload's digest. Bind the original idempotency key to a server-keyed digest of the exact raw file bytes and normalized declared MIME, so files with different private metadata cannot become the same request merely because sanitization yields the same bytes. Do not persist raw file metadata or the caller filename in the receipt. A fresh upload of already verified sanitized content can reuse an existing Media with its actual revision, without implicitly attaching it to an owner. A new identity starts at revision one. Thumbnail JPEG bytes have their own digest; perceptual hashes and visual indexing remain separately validated features, not proof that two photos depict the same object.

A safe implementation must use a private staging area, durable file/directory synchronization, atomic promotion under a server-controlled content key, and recovery for crashes on either side of SQLite COMMIT. Source, counters, current/outbox, audit, idempotent response and any pending-cleanup record commit together. File cleanup runs only after commit and rechecks references, so failed writes, original-key reconciliation, duplicate content or a shared object cannot lose data. Metadata, thumbnails, private originals, receipts and credentials must not enter logs or public caches. A service worker must not cache protected API responses or originals; any future opt-in thumbnail cache has its own privacy and purge policy.

## Image processing groundwork

The internal `server/internal/mediaimage` utility currently accepts JPEG and PNG bytes only. It checks the declared MIME without parameters against the actual format, applies the 32 MiB input, 16,384-per-dimension and 64-million-pixel ceilings before full decoding, and permits callers to specify stricter limits. PNG chunk framing and CRCs are checked across the entire file; APNG control/frame chunks are rejected. JPEG segment and scan framing requires one complete image with no appended data. Malformed or duplicate EXIF orientation is rejected rather than guessed. Input may already occupy memory: a future HTTP boundary must independently bound and stage the multipart stream before calling it.

After complete decoding, the utility applies the eight TIFF orientation values, then re-encodes JPEG at quality 90 or PNG with the standard Go codecs. The output drops source metadata, including GPS and color profiles; stripping color profiles can change displayed colors. The result's MIME, dimensions, byte count and SHA-256 describe the new bytes, not the raw request. Distinct files with different private metadata can produce identical sanitized bytes: future upload idempotency must still bind a server-keyed digest of the exact raw bytes and normalized declared MIME. Visible GPS text in image pixels is not removed. On any error the caller must discard the entire output. One process-wide decode slot limits simultaneous image processing; large images can still require substantial memory, cancellation is cooperative, and future admission must separately limit concurrent staging.

Tests use generated image pixels, actual GPS-bearing EXIF, eight orientations, progressive JPEG scans, 16-bit alpha PNG, malformed/truncated data, CRCs, APNG, limits, cancellation and fuzzing. This is an internal byte-processing component, not an upload handler, thumbnail generator, private file store, file-integrity check, recovery protocol or proof of real-device acceptance. **WebP still needs a supported decoder and complete container/animation validation before the contracted upload can be enabled.**
