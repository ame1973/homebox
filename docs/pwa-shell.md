# Public Shell and Updates

HomeBox's production build creates a versioned service worker for the public application shell. On a first secure visit, the application attempts to prepare it when browser support and the current deployment can be confirmed. The shell can open without connectivity after installation and while browser storage survives; it contains no private offline inventory, photos or drafts. Installation is browser-dependent, and storage can be evicted. It is not a backup or a substitute for authentication.

## Build and installation boundary

`npm --prefix web run build` enumerates the Vite entry, lazy chunks, emitted workers and a fixed list of public icons and manifest files. It rejects unsafe or unhashed asset paths, missing dependencies, more than 256 resources, an individual file over 4 MiB or more than 16 MiB of public shell bytes. The worker URL and cache name change when the shell, asset bytes, worker source or build generator changes. The built HTML identifies the root-scoped worker.

The same build writes `/pwa-version.json` with the exact worker URL. The Go server serves only that JSON filename as a public asset with `no-store`; the worker does not cache or answer it. This public descriptor is groundwork for checking the currently deployed shell, not an API compatibility handshake, an atomic deployment guarantee or authorization to replace an existing registration. A successful build must publish the HTML, descriptor, worker and hashed assets together; an incomplete deployment can produce mismatches. The generator refuses to overwrite an existing descriptor in its build directory. The internal browser reader sends one same-origin, cookie-free, non-cached request with an eight-second deadline, validates the status/MIME/cache policy, bounds streamed bytes and accepts only the build's exact versioned path. It does not itself register a worker, retry a request or prove that a version is safe to activate.

During registration, installation downloads only these public resources without credentials. It checks each response's status, MIME type, exact byte length and SHA-256 before putting it in the versioned shell cache. The public `/` supplies the HTML because the Go server redirects `/index.html`; the verified HTML is retained under the offline cache key `/index.html`. Failed installation cannot activate the new worker and does not delete the previous shell. Installation may leave a partial new cache for a later attempt; no automatic cache deletion is performed.

The application observes the root registration and, only for an empty root, prepares the first worker after checking that the live descriptor matches the current document. Later registrations require an explicit user action and a fresh matching descriptor. A Web Lock serializes cooperative HomeBox tabs while registration is pending; it rechecks actual root/current-page registrations and does not overwrite a foreign worker, a different waiting/installing worker or a stale document's version. A root can appear between the separate browser reads; the coordinator checks both observations and uses the later matching root rather than labeling a valid concurrent installation foreign. Browsers without secure service-worker and Web Locks support cannot use this coordinator and remain usable online. After a failed first attempt, retry is explicit. Visible pages periodically recheck the public descriptor; page suspension cancels pending checks and BFCache restoration performs a read, not automatic registration. The browser's native registration cannot be canceled once sent, and a stopped caller holds the lock until its promise settles. This coordination does not prevent uncooperative same-origin scripts, browser process termination or deployment changes after the final check. Script-path recognition is not authentication.

## Request and privacy boundaries

- Authenticated API, account, Media, backup, export, worker, private-data and development namespaces are never cached or answered by a shell fallback. The worker ignores non-GET, cross-origin and Range requests. Signed-in responses and mutation requests are not queued or replayed.
- A cached asset is checked again against the build's exact byte length and SHA-256 before use. Returned cached HTML and assets receive the application's strict CSP, `nosniff`, frame, referrer and permission policies rather than trusting mutable cache headers. A missing or corrupted cached hash-named asset may be fetched from the network, but the worker verifies its status, MIME and bytes before returning it. `no-store`, reload and query-bearing hash-named requests do not use Cache Storage, but still require that network verification.
- Extensionless public document navigation and the unversioned public manifest/icons use network-first behavior. A non-redirected successful network body is limited to 4 MiB and its network request and body are bounded by an eight-second abort; an unreachable or invalid response can fall back to the verified old shell. HTTP errors are not silently converted into successful pages. A canceled navigation is not intentionally completed from a cached shell.
- The exact size limits bound the application's own retained buffers, not every browser, native network, cryptographic or Cache Storage allocation. Browser cache access and native operations may fail or stall independently; storage can be evicted. The shell is not an encrypted vault or a security boundary against arbitrary same-origin code execution.

The worker never calls `skipWaiting` or `clients.claim` and never deletes old shell caches. The application shows the worker state and a deliberate preparation action for a current page. If an older page detects a new deployment, save unfinished work and reopen the page before preparing the update. After preparation, **save work in every HomeBox tab, close all tabs using the old worker, and then reopen the application**: the browser normally activates the waiting worker after its old controlled clients have closed. There is no forced refresh or claim of another tab. A first installation likewise does not control the page that registered it; later navigations can use the shell. Browser-managed automatic checks of an already registered script are still possible: never replace bytes at an existing content-bound worker URL.

The descriptor does not provide the required API/client compatibility handshake, and the application does not yet migrate an offline replica or persistent drafts. A private, completed-session database read can validate the dataset identity, projection version and full migration checksum history after session activity; it is not an HTTP endpoint or a compatibility decision. The worker's content hash identifies a shell but is not an ordered release version. Protected writes currently accept only the exact client versions `0.1.0` and `0.1.0-dev`. Old shell cache versions can accumulate until a reviewed cleanup workflow exists. A waiting state does not mean every tab has saved its work or that all cached bytes remain intact.

## Development checks

```sh
make build-web
npm --prefix web run test:build
npm --prefix web run test:e2e -- tests/e2e/shell-worker.spec.ts tests/e2e/shell-monitor-api.spec.ts tests/e2e/shell-indicator-ui.spec.ts --workers=1
```

The browser tests use disposable Go databases, isolated browser storage and Chromium emulation. They exercise real worker installation, offline navigation, actual private API reads, malformed and evicted cache content, unexpected 201/206 responses, delayed network, and two-tab update waiting. Unit tests separately simulate cancellation, oversized responses and a response body that stalls after headers. These are not physical iPhone/Android or QNAP acceptance, a full offline-replica test, or authorization to operate on existing Media files.
