# Offline Replica and Safe Draft Protocol

SQLite is authoritative. IndexedDB is a disposable per-device read replica, not a backup or an offline write authority. Protocol projection version is `1` for the first application release.

**Current implementation:** the protected, no-store `GET /sync/status` reports materialized projection counts, the durable allocated change watermark, the retained floor and the highest retained change's timestamp. It explicitly returns `bootstrap_ready: false` and `retention_enabled: false`: the diagnostic is not proof of complete backfill, source integrity, retained-history completeness, working bootstrap/delta or automatic pruning. Missing count keys mean zero materialized rows, not zero source records. The 30-day minimum is a retention policy, not a claim that a pruning job exists or that the oldest row has that age. See [Sync Status](../docs/sync-status.md).

The protected [authenticated connectivity probe](../docs/connectivity.md) is available as a minimal no-store read with an eight-second stateless browser adapter. It verifies a completed session without renewing idle activity, but it does not start sync, establish source or storage health, or measure device coverage. The application shell displays foreground probe results with bounded retry/backoff after a completed session check; existing page-specific online controls still treat the browser signal as advisory and handle their own failures.

## Record identity

Every record contains `entity_type`, `entity_id`, `entity_revision`, `operation`, `projection_version`, and `payload`. Upserts contain a full validated projection; deletes contain null. Revisions are monotonic per logical identity, and the durable change-log sequence is globally monotonic.

| Entity | Identity |
| --- | --- |
| location, item, unit, barcode, media, media_link, category, tag | Stable row ID |
| alias, attribute, purchase, purchase_line, usage, cost, ai_review, events | Stable row ID |
| stock | Canonical JSON pair `[item_id, location_id]` |
| item_tag | Canonical JSON pair `[item_id, tag_id]` |
| search_doc | Canonical JSON pair `[entity_type, entity_id]` |
| asset, disposal | `item_unit_id` |

Composite keys use the canonical JSON string-array spelling produced by `JSON.stringify`: no insignificant whitespace, ordinary non-ASCII/HTML/slash/U+2028/U+2029 characters stay literal, quotes/backslashes and control characters are JSON-escaped, and hexadecimal control escapes use lowercase. Bound and validate each original ID independently; do not apply a single 128-code-point ID limit to the encoded pair, normalize Unicode, repair invalid UTF, or accept alternative escaped spellings as another identity.

A barcode's normalized value is a nonunique lookup index, not its primary key. Media has no owner; independent media-link rows provide many-to-many ownership. Removing one link must not delete another owner's image. Quantity projections use integer `quantity_base`, not `quantity_minor`.

## Transactional publishing

Every business mutation runs inside one immediate SQLite transaction:

1. Validate authentication, revisions, idempotency, and business invariants.
2. Modify authoritative domain records and append immutable events.
3. Rebuild affected approved search documents and projections from final transaction state.
4. Increment each changed logical projection revision and append its frozen upsert/tombstone.
5. Save the idempotent reply and invalidate relevant analytics revisions.
6. Commit everything or roll back everything.

Raw SQL writes outside transaction-aware domain services are forbidden. Initial legacy backfill must publish every existing eligible row before enabling sync. Exceptional bulk changes that cannot enumerate every affected projection rotate the epoch atomically; they cannot leave silent replica divergence.

The server's shared strict JSON checks reject invalid UTF-8 and unpaired surrogate escapes, and parse bounded safe integers exactly without floating-point rounding. These checks are available to future frozen-projection readers and preserve the existing HTTP input behavior; they do not by themselves validate projection schemas or authorize publication.

An internal Go payload validator compiles the supported flat scalar definitions for all 22 version-one kinds from an embedded, byte-for-byte copy of [`offline-projection.schema.json`](offline-projection.schema.json). It rejects malformed or lossy JSON, duplicate or unknown properties, unsupported payload-schema grammar and invalid field values without rewriting the supplied bytes. Root and embedded schema copies are compared by the contract suite; a definition that needs a new keyword, type, pattern or format must be reviewed and supported before use. The validator deliberately adds a 128-byte number-token limit and JavaScript-safe integer bounds even where the schema alone is broader. Its date-time check rejects year zero, leap seconds and non-RFC 3339 spellings, including a trailing newline that the Python format checker currently accepts. These stricter rules can reject otherwise schema-valid historical data; callers must fail closed rather than silently change retained bytes.

The payload helper validates a **payload only**. A separate private Store check composes it with a supported kind, version-one marker, safe positive revision, operation and exact row identity. It requires a SQL NULL payload for a tombstone and compares stock, item-tag and search-document identities using the existing canonical pair spelling; other upserts bind their independent ID or Unit-owned identity. Neither helper parses a serialized record envelope, checks an authenticated session, verifies source completeness, or proves that `search_doc.approved_text` actually came from reviewed sources. Callers must bound total payload/page sizes before validation and perform those authority and provenance checks in the same authorized transaction as their frozen reads. Neither helper alone enables public bootstrap or delta; synthetic and selected-producer tests do not make sync ready.

A separate, read-only private check can compare a selected **current** search payload to text freshly derived in the same transaction from actual Item/Unit metadata, scoped purchase evidence, and accepted or corrected, reviewed free-text suggestions. It does not use search or FTS caches; an unreviewed candidate or raw OCR is not a source for this text. The caller must still establish that the supplied bytes and revision are the actual current row and counter, bound payload and page sizes, and authorize and revalidate the session. Source text aggregation may grow with the underlying records. This check must **not** be applied to a historical delta against today's source: earlier frozen text can legitimately differ after an authorized change and must remain byte-for-byte unchanged. The check neither backfills missing documents nor establishes complete source coverage.

Another private, read-only check validates a supplied version-one current record, matches its exact bytes and revision to the actual current row and independent counter, bounds and validates the retained `updated_at` text without interpreting its chronology, and compares its fields with freshly read source in the same transaction. The non-search source serializer is shared with domain publication and does not rebuild FTS. For those kinds, both supplied and regenerated payloads pass strict schema and identity validation before semantic comparison; search documents instead use the approved-source check above. Equivalent stored JSON spellings are preserved without accepting different bytes as the stored row. Current `ai_review` source serialization is not implemented and fails closed, even for a schema-valid row. This check neither proves every dependent owner, parent, history or cross-domain invariant nor establishes eligible-source completeness, authorization, retention or Media file integrity. Its 64-MiB payload ceiling does not bound SQLite allocations, source reads, search aggregation or intermediate copies. Do not use it to rewrite source, certify historical deltas, sign an incomplete snapshot or enable public synchronization. A future producer must recheck the relevant source, current rows, counters, signer and session after any later trigger-capable writes and before commit.

A private Location-only coverage check examines all retained Location source rows in one caller-owned transaction, including archived and logically deleted rows, using batches of at most 100 exact IDs. It validates selected Location fields and each independent counter; for a live Location it also validates the real nondeleted ancestor chain and matches the actual current projection to source. A retained deletion marker must be bounded nonempty UTF-8 text, and a deleted Location must have no current Location projection; the check does not interpret marker chronology or validate source creation/update timestamps. It rejects extra current Location rows without a live source and withholds all counts on any failure; it does not repair data. It does not validate deleted-source ancestry, historical tombstones, other projection kinds, cross-domain links, session authority, retention or a complete snapshot. Its ID batches and per-payload ceiling do not bound overall work, source/SQLite allocations or repeated ancestor traversal, and target-NAS performance is unmeasured. A caller must keep all checks in the authoritative transaction and repeat the relevant checks after later trigger-capable writes; this observation is not permission to enable bootstrap.

A separate private check covers retained Location movement rows and their current projections within one caller-owned transaction. It validates each event's identity, bounded occurrence text and independent counter, checks that its historical parent identities still exist even if logically deleted, and verifies the retained owner's selected source, counter, deletion state and applicable current projection and live path. It verifies exact persisted event bytes and the independent counter before semantically comparing selected source fields, and rejects extra event projections without source. Missing or invalid data withholds the whole count. It does not validate historical parent fields or ordering, prove that all historical events or tombstones survive, establish unrelated Location coverage or other kinds, authenticate a session, perform retention, or produce a snapshot. It checks event owner/parent IDs and occurrence-text byte ceilings in SQL before reading those source fields into Go; SQLite itself and other source/owner reads may still allocate more. The 100-ID batch and 64-MiB payload limits do not bound total work; owner and ancestor validation repeats per event, with target-NAS performance unmeasured. A complete producer must independently verify all required sources and recheck the applicable state after later trigger-capable writes before committing.

A private taxonomy check likewise traverses all present Category and Tag source rows in the caller's transaction. It validates their selected fields and independent counters, checks each actual Category ancestor path for missing parents or cycles, compares exact stored current rows and counters to source, and rejects current rows with no matching source. It returns counts only after both kinds pass. Category and Tag deletion physically removes source; retained counter-only identities are not classified, validated as deletions or treated as tombstone-history proof by this check. It neither verifies Item/Tag memberships and search dependencies nor establishes session authority, complete cross-domain coverage, retention or a snapshot. The 100-ID batch and per-payload ceiling do not bound total source/SQLite allocation or repeated Category ancestry/text derivation; target-NAS costs are unmeasured. Any later trigger-capable writes require relevant revalidation in the same transaction before commit.

A private Item check traverses all present Items, including archived ones, after reading the actual dataset and durable watermark/floor in the caller's transaction. For each it validates selected source fields and its independent counter, checks any selected Category's source, path and current projection, matches the actual current Item projection, and requires a current search projection derived from actual approved Item source. The existing search check also rejects counters behind retained change or same-dataset snapshot revisions; it does not authenticate historical proofs. Missing or inconsistent source/current data and orphan Item projections withhold the entire count. This check does not classify counter-only deleted Items, find orphan or malformed search projections not attached to an enumerated Item, certify every related link/owner/history or source timestamp, check session authority, implement retention, or produce a snapshot. Its per-record cap and 100-ID batch do not bound SQLite/source allocation, reviewed-text aggregation, retained-history queries or total work; target-NAS performance is unmeasured. A complete producer must check the other sources and revalidate all affected state after later trigger-capable writes before commit.

A separate private approved-search check traverses all present Item and Unit sources, including archived Items and disposed Units, in one caller-owned transaction. It requires a current search projection for each source, validates its exact identity/revision and approved text against real source, and checks its counter against retained change and same-dataset snapshot revision bounds. It also traverses every current search identity, rejecting noncanonical, unsupported, oversized or orphan identities and mismatched source/projection counts. All counts are withheld on any failure; no FTS/search cache is used as source authority or repaired. This is coverage of current search only, not proof of historical HMACs, deleted counter-only identities, complete Item/Unit current projections, every related source/counter, session, retention or a snapshot. ID batches and payload limits do not bound SQLite/source allocation, approved-text aggregation, history queries or total work; target-NAS performance is unmeasured. All required sources, signer and session must be rechecked after later trigger-capable writes before a future producer commits.

A private Unit check traverses all present Units in one caller-owned transaction, including disposed and unlocated Units. It validates each Unit and its independent counter, the real individual-tracking Item source and counter, any real nondeleted Location ancestor path, and the exact current Unit projection against source. Extra Unit projections without source and any invalid or missing data withhold the entire count. This does not validate Item/Location current projections, search coverage, physical events, deleted counter-only identities, every cross-domain relationship, authorization, retention or a snapshot. Its bounded ID batches and payload ceiling do not bound total source/SQLite allocations or repeated ancestor reads; target-NAS performance is unmeasured. A future producer must check every other required source and revalidate affected state after later trigger-capable writes before committing.

Derived effects matter: changing category/tag/alias/purchase/review data may change item search; moving a unit changes its location evidence; deleting an owner emits media-link tombstones. Paths are derived from parent links rather than copied into every descendant projection. Unreviewed OCR and rejected suggestions never enter published search documents.

## Financial correction effects

The [audited financial correction contracts](../docs/financial-corrections.md) define current accounting effects without another replica kind. Allocation correction retains the original posted Line and may create a new independent replacement, but publishes an old-Line tombstone so retained audit source cannot resurrect a voided current attribution. Disposal correction retains the first posted decision and every immutable correction, publishing only the actual current financial decision or a tombstone for explicit void. An intentional zero-valued current decision remains an upsert, not a void.

Existing `purchase_line`/`disposal` identities, version-one payload shapes and the 22-kind envelope remain unchanged. Source, correction/audit, real independent revisions, affected financial/search scopes, frozen upserts/tombstones and original response must commit atomically. Never rebuild effective values from current/FTS caches or overwrite old frozen bytes. Detailed authenticated correction history is not a second offline authoritative ledger; physical status/placement and movements are not undone by financial void. Migrations 0017/0018 and private Purchase and Disposal correction/history services implement these source/current-effect boundaries, including validated void gaps, complete linked Disposal history and fail-closed damaged context. The five correction HTTP operations and reviewed correction browser workflows expose those boundaries, but the full frozen sync protocol remains unimplemented; partial publication is not sync readiness.

## Frozen bootstrap

`GET /sync/bootstrap` starts a short-lived materialized snapshot. In one immediate transaction, read server identity, dataset epoch, projection version, and change-log high watermark `H`, then materialize all current eligible projections in deterministic `(entity_type, entity_id)` order. Paginated responses read only these frozen rows, never live joins.

Snapshot cursors bind server instance, epoch, projection version, snapshot ID, next ordinal, and expiry with an HMAC or an equally strong server-side token. The default lifetime is 15 minutes. Snapshot expiry returns `410 SNAPSHOT_EXPIRED`; do not garbage-collect unexpired snapshot pages.

The internal cursor codec now signs independent snapshot and delta purposes with the private server key. Snapshot tokens bind the principal, exact dataset identity, snapshot ID, ordinal, high watermark and nanosecond-precision 15-minute interval. Delta tokens bind the principal, exact dataset identity and sequence without a wall-clock expiry; a later authorized database read must compare the sequence with the actual retention floor and allocated watermark in the same transaction. The codec authenticates a bounded canonical token but does not authenticate a session, materialize a snapshot, check the stored snapshot row or implement either HTTP route. Tokens are integrity-protected, not encrypted: never put credentials or private record data in them. Incompatible signed dataset scope requires reset; a changed or missing signing key cannot be distinguished from tampering.

A separate private metadata read now checks a completed session and the actual database signing key, binds a snapshot cursor to the stored ready manifest and exact timestamps, and checks its high watermark against the current inclusive retention floor and durable allocated watermark. It verifies any independent snapshot signer before and after session activity and rejects an unexpected presence change; an absent signer does not certify old content. It counts the snapshot's ordinal range and refuses gaps or an out-of-range cursor; a missing or prematurely expired manifest before the signed expiry is inconsistent state, not evidence that expiry was honored. The session and exact expiry are checked again before commit. This read returns no projection payloads, does not create or delete snapshots, and does not establish row-content integrity, immutability or a stable count across reads, reviewed search provenance, deterministic entity order or complete source coverage. Counting may grow with snapshot size. The helper does not enable bootstrap or delta HTTP.

Private HMAC-SHA-256 helpers can bind a declared snapshot row count and each row's exact bytes under separate manifest and row domains. Both include the administrator, instance, epoch, snapshot ID, exact creation/expiry timestamps, cursor/projection versions, high watermark and total. A row additionally binds its ordinal, supported kind, canonical identity, revision, byte length and payload. Strings use an eight-byte big-endian byte-length prefix; integers use eight-byte big-endian encoding. The pagination ordinal is validated but intentionally excluded from the stable proof. Empty snapshots can have a manifest proof; row payloads must contain at least one byte and are capped at 64 MiB before hashing. This is a source-field limit, not an HTTP or total-memory limit, and hashing checks cancellation in chunks.

These helpers accept opaque bytes and do not validate JSON, prove reviewed source or completeness, authenticate a session or check the database key. Migration 0029 creates initially empty manifest-seal, row-proof and independent signer-dependency tables; it preserves all old snapshots without assigning them a signer or proof. A seal requires a ready manifest, a contiguous ordinal range and one stored 32-byte proof for each row, but these SQL constraints do not validate an HMAC or approved source. Sealed manifests and rows cannot be updated or replaced, and seals/proofs cannot be directly removed while their parents exist. Seal checks count the snapshot rows and proof rows, so their cost grows with snapshot size. A sealed snapshot with hidden rowid `-1` makes automatic snapshot insertion fail closed because SQLite also exposes `-1` before allocating an automatic rowid. Explicit deletion of a snapshot still cascades to its rows and proofs: a future retention operation must itself prevent deletion before expiry.

Authentication refuses to regenerate a missing server key while a snapshot signer, seal or row proof remains, including proof state injected during key-initialization audit. The first snapshot-signer pin refuses unknown existing seals or row proofs and rechecks the key, both other signer dependencies and proof-table emptiness after insertion. Search-signer pinning, new search publication and new keyed Media commands likewise preserve the independent snapshot signer; original-key Media receipt replay does not require current snapshot state. An unknown unpinned proof with its existing key can remain as untrusted data; it cannot be assigned a newly guessed signer. None of these constraints establish source completeness, reviewed provenance, valid MACs or authorization.

A private snapshot-page reader now performs completed-session activity, validates the actual key and signer, matches the signed cursor to the stored manifest and retained watermark/floor, and verifies the sealed count and HMAC in the same SQLite transaction. It reads bounded frozen rows in ordinal order, validates version-one payload shape and identity, and compares each stored row proof with the exact bytes. It also validates one lookahead and, after the first page, one previous-row anchor to check `(entity_type, entity_id)` ordering across the page boundary. An invalid or unproven row withholds the whole page; no source or cache repair occurs. It rechecks the session and exact expiry before commit. The final page returns an internally signed delta cursor at `H`; earlier pages return a signed snapshot continuation. Counting can grow with snapshot size. The trusted caller's page budget bounds returned source fields to at most 64 MiB, but the anchor, lookahead, SQLite allocations, copies and future HTTP encoding are additional.

A matching proof authenticates only the bytes signed by a trusted producer, not their approved source or completeness. No authoritative snapshot producer or source-coverage gate exists yet; test fixtures construct selected seals directly and do not establish production provenance. A full traversal from ordinal zero is needed to check ordering across all page boundaries. A future producer must validate all authoritative source and approved search in the same authorized transaction, pin and recheck the actual key dependency, and persist the seal and row proofs before any public exposure. The private reader does not establish retention, implement an HTTP route or make bootstrap ready; an actor with unrestricted database and schema access can also read the signing key.

The browser stores each page and its cursor atomically in a staging namespace. Partial bootstrap data is not presented as a complete replica. The final page has `complete=true`, `next_cursor=null`, and a server-issued `delta_cursor` for `H`. Publish staging and this cursor in one IndexedDB transaction. Never construct signed cursors in the browser.

Changes after `H`, including deletions, are consumed through delta sync. An expired bootstrap discards staging only, preserving the previous published replica and all drafts.

## Ordered deltas and retention

`GET /sync/changes?after=...` returns frozen change records in sequence order, a high watermark, a next cursor, and `has_more`. Read the JSON stored at commit time, not current mutable rows. Empty pages retain the cursor's sequence. Apply all rows, dependent invalidations, and cursor advancement in one IndexedDB transaction.

A private Store reader now checks a completed session, performs session activity, then verifies the actual database signing secret and any pinned key dependencies before reading the dataset identity, durable watermark and signed cursor in the same transaction. It validates each retained record and the lookahead, preserves the original payload bytes and SQL-NULL tombstones, and rechecks the session before committing. A trusted caller supplies per-record and per-page source-field byte budgets; the latter is at most 64 MiB for returned records. A lookahead up to the per-record budget, intermediate copies, SQLite allocations and proof bytes are additional, and no future serialized HTTP response is bounded by these limits. A record that cannot fit even on an empty page fails without returning a prefix, and a page may contain fewer than its requested records when the page budget is reached. For each search upsert, including lookahead, the reader requires the pinned search signer and verifies its stored HMAC against the exact frozen bytes, identity, revision, sequence and current dataset scope. A missing, malformed, copied or mismatched proof withholds the whole page; a validated search tombstone contains no text and needs no proof. Unexpected proof rows on other kinds or tombstones are invalid state. The reader never compares a historical search value with today's source, which may legitimately have changed or been deleted. It does not prove provenance for other retained kinds, source completeness or a valid bootstrap. This internal reader is not an HTTP endpoint, does not issue a bootstrap cursor or perform retention, and must not be exposed as working synchronization until those gates and wire-size policy are complete.

A separate private version-one HMAC helper binds the exact server instance, dataset epoch, canonical search identity, sequence, revision and original payload bytes using the server secret and a search-specific, length-framed domain. It processes payloads in cancellation-aware chunks, and its caller must retain an unchanged byte slice. The HMAC alone does not validate JSON, prove reviewed source, authenticate a session, check the current database secret, store a proof or authorize a read. The domain mutation publisher uses it for new source-validated changes, and the private delta reader verifies the persisted binding. Legacy changes without a valid proof remain withheld.

Migration 0026 adds initially empty private storage for a 32-byte proof associated with a retained search upsert. Existing changes and current projections keep their exact bytes and receive no guessed proofs; a late migration-ledger injection causes rollback. Rows cannot be updated, replaced or directly deleted while their parent remains; deleting the associated retained change cascades to its proof. The table checks only the parent kind/operation and byte length: an arbitrary row is not evidence of reviewed source or a valid HMAC.

Migration 0027 adds a separate, initially empty search-signer key dependency. The private pin helper verifies the actual server key and any existing Media receipt dependency, refuses a first pin while unknown proof rows already exist, and rechecks the key, both marker presences and empty proof table after insertion. Authentication refuses to regenerate a missing server key while either a search-signer marker or any search proof remains; its initialization transaction also rejects a late injected dependency. An unknown unpinned proof does not itself block ordinary authentication when the original key exists, but it cannot be assigned a newly guessed signer. The marker is independent of the keyed Media receipt marker, which cannot be reconstructed from it. These checks bind a key, not approved source or a particular change. The delta reader checks any pinned search signer after session activity and accepts only search changes with matching proofs.

For a new domain-produced search upsert, the same authorized mutation snapshots the dataset scope and both signer-marker presences before source writes, derives and validates approved Item/Unit source, pins the signer and stores the exact bound proof alongside the current projection, frozen change, audit and idempotent receipt. It permits the actual keyed Media operation to establish its own marker during that transaction. After session activity and the last optional final callback, it rechecks the key, marker presences and dataset, actual source, counter, exact current/frozen bytes and timestamps, and stored proof; session and receipt are checked again before commit. Failed checks roll back the mutation and proof. A tombstone needs no text proof, and an original-key replay does not invent another proof. Source aggregation may grow with the underlying records. This covers only newly published search changes, not a legacy backfill, other projection provenance, or complete synchronization. Proof validation relies on the transaction-aware producer and protected database key; it is not a defense against an actor with unrestricted database and schema access who can also read that key.

A private single-source search backfill can explicitly rebuild one missing Item or Unit search projection from actual approved source. A new command requires a completed session, the original Item revision and, for a Unit, its original independent revision, plus a session-bound reauthentication grant consumed in the same transaction. Grant state is checked after audit and session activity; the raw capability is not part of the receipt or audit. An explicit original-key replay needs a completed session but does not consume another grant. An existing valid current projection is left byte-for-byte unchanged with a receipt-only acknowledgement; invalid or source-inconsistent current data fails without repair. The operation checks the durable watermark, retained floor, highest retained search revision and same-instance/epoch/version snapshot-row revision for that identity before and after publication. A missing counter can be initialized only when the floor is zero and neither retained history nor a same-dataset snapshot names the identity; an existing counter must not lag either. This relies on the retention floor accurately recording pruning; arbitrary out-of-band deletion is not evidence that an identity had no history. The guard does not validate complete snapshots. Migration 0028 adds partial per-identity search-revision indexes for retained changes and snapshot rows; the number of matching records and source aggregation can still grow, and query-plan tests do not establish target-NAS performance. The acknowledgement revision belongs to the search projection, not to the Item or Unit. The operation does not change Item/Unit revisions or physical/financial source. This is not an HTTP endpoint, batch/job coordinator, complete coverage check or permission to enable bootstrap; callers must not infer that one successful source represents a full backfill.

A private live coverage page can locate current or missing Item/Unit search projections without returning source text. After completed-session activity it validates the actual database signing key and dataset, the catalog revision, each real Item/Unit and independent counter, search history/snapshot revision bounds, and the actual approved source. Invalid source or lookahead fails the entire page. It returns up to 20 source identities and original owner/Unit revisions, together with current presence and any retained search revision; a valid current row is not proof that its historical changes are signed. Archived Items and disposed Units remain in scope. The 15-minute signed, unencrypted continuation binds principal, epoch, server instance, kind, page size, allocated watermark, retention floor and catalog revision. A projection-producing domain change, including a search backfill that publishes a row, requires restarting the live traversal; a fresh session of the same principal may continue only while the scope remains unchanged. Retention, snapshot rows, source changes outside domain services, and corruption may have independent lifetimes, so even a completed traversal is not a frozen coverage certificate. Source aggregation and matching retained history can grow with underlying data, and the row limit is not an absolute memory or time bound. This private read is not an HTTP endpoint, batch authorization, proof of other projection kinds or permission to enable bootstrap.

Duplicate/overlapping pages are safe: retain the latest `(epoch, entity_revision)`, including tombstone revisions, so a stale upsert cannot resurrect a deleted row. Deleted or revised media invalidates matching thumbnails/vectors; removing a media link only removes that link.

`min_retained_seq` means the last pruned sequence: a cursor exactly at the floor is valid, while a cursor below it requires bootstrap. Keep at least 30 days of changes by default. Current projections are stored independently of retained history, so log pruning cannot remove records from a future bootstrap.

Wrong epoch, instance, incompatible projection, or an expired retained cursor returns `410 SYNC_RESET_REQUIRED`. A tampered cursor may return 400. Restore/reseed generates a new epoch before accepting any traffic; numeric sequence coincidences never allow an old dataset cursor to pass.

Only one tab coordinates sync, using Web Locks or an expiring IndexedDB lease. Other tabs read committed state. No sync coordinator submits drafts.

## Local privacy, drafts, and models

- Standard mode synchronizes all searchable metadata and approved OCR. Lite mode keeps visited data; complete mode offers opt-in thumbnails/vectors/originals after size estimates.
- Store no authentication/CSRF/worker/cloud secrets in IndexedDB or localStorage. Logout clears private replica/cache state after a draft-loss warning.
- Drafts and attachment blobs are separate stores and survive replica resets, expired snapshots, epoch changes, and compatible schema upgrades. Quota pressure never silently deletes drafts.
- Offline operations are proposals only. On reconnect, show differences, revalidate, and require explicit foreground confirmation through normal domain endpoints with current CSRF, idempotency, and revision preconditions. `/drafts/validate` is advisory and cannot bypass domain validation.
- Model installation is explicit, size-bounded, and SHA-256 verified before promotion. A failed upgrade preserves the previous compatible model. Model key, preprocessing, dimension, normalization, and source image digest must match vectors.
- Local image search reports coverage and cannot assert that an item is absent when vectors/images are missing. Camera capture remains real live capture even offline where the platform permits it.

Service workers cache the app shell and versioned static assets, not protected API responses. Updates wait for explicit approval and preserve unsaved work. Browser storage can be evicted and cannot be remotely wiped while disconnected. The application attempts initial registration of its integrity-checked public shell in supported secure browsers, and offers explicit preparation of later versions without forcing other tabs to reload. This does not implement a browser replica, persistent drafts or the required API/client compatibility handshake. The deployment, update and cleanup limits are described in [Public Shell and Updates](../docs/pwa-shell.md).
